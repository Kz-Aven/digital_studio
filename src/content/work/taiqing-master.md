> **项目概览**：企业级 Agent 平台是面向企业的数智员工创造与管理平台。企业用户可以通过自然语言描述工作需求，由 Master 协助匹配技能、知识、数据与设备能力，并通过授权使数智员工参与实际业务工作。产品已正式上线，采用会员订阅模式。

**我的角色**：主导 Agent 产品体系的规划、需求分析、核心交互与流程方案，并与研发团队协作推进落地。职责覆盖数智员工创造、Skill 接入、知识库与数据连接器、智能体手机关联、权限设计，以及 Evals / Benchmark 方案设计。

## 01 / 背景：从智能体手机到企业人机协作

2025 年，团队已经推出智能体手机，通过自动化方式帮助用户完成部分日常工作。但当时产品能力主要集中在任务执行，人和智能体之间尚未形成完整的协作体验。

2026 年初，OpenClaw 等个人 Agent 产品引发市场关注，体现出 Agent 从孤立工具向持续协作助手发展的趋势。我们判断：企业内部同样存在人机协作的空间，但企业场景不仅要求“能执行”，还要求接入业务数据、理解专业知识、管理权限，并与既有组织流程协同。

因此，Master 的产品方向被定义为**面向企业的数智员工创造平台**：企业能够创造自己的数智员工，赋予岗位能力，并让其与真人员工共同完成任务。

## 02 / 用户与定位

平台面向具有一定数字化基础的 B 端企业，制造业是具有代表性的目标行业。购买决策通常由企业经营者作出，部门管理者负责组织业务场景，一线员工与数智员工协作。销售部门已有的通话录音、生产部门已有的设备数据等，可能成为数智员工发挥作用的数据基础。

产品定位并非单一行业的自动化工具，而是将**岗位目标、技能、企业知识、业务系统、设备和授权**组织在一起的通用企业数智员工平台。

**核心产品命题**：企业需要的不是一个拥有大量工具的 Agent，而是一个能够承担具体工作的数智员工。

## 03 / 设计决策一：让用户描述工作，而不是配置技术

### 问题

创造数智员工涉及 Skill、知识库、系统连接、权限和设备等概念。企业业务人员知道自己缺少什么样的员工，却未必理解这些技术配置。

### 设计判断

招聘真实员工时，业务负责人通常先描述岗位要求，由 HR 协助完成招聘流程，而不是亲自处理每个专业步骤。创造数智员工也可以遵循同样的心智模型：用户描述需要什么样的员工、承担什么职责；Master 反向分析所需能力，并呈现待确认与授权的配置。

例如，用户希望创造一个能够分析销售录音、总结客户需求并整理到 CRM 的销售助理。Master 应据此推荐通话分析能力、相关知识以及 CRM 访问权限，由用户确认和授权。

**设计原则：让用户定义工作，让系统组织能力。**

### 一次真实的可靠性取舍：智能体手机配置

最初，团队将智能体手机已有能力封装为 MCP，并尝试通过标准化 Skill 让 Master 自主调用、完成设备配置。早期测试顺利，但随着上线后用户使用增加，出现模型未找到 MCP 工具、未调用 Skill 等问题，导致配置失败。优化 Skill 能改善部分成功率，却不能根治工具选择的不确定性。

随后团队调整方案：由 Master 在设备配置场景中调起**确定性 Workflow**，让关键设备配置沿可控路径执行。这样会增加部分交互步骤，但在相对低频、可靠性要求较高的企业设备配置中，团队认为这种取舍是值得的。

**复盘**：Agent 的自主性不是越高越好。开放式理解与判断适合交给 Agent；涉及关键配置的确定性操作，应根据任务风险与稳定性要求选择 Workflow。

## 04 / 设计决策二：从一句业务目标反向组织工作能力

### 典型场景

以制造企业的需求为例：“我需要一个生产管理助理，每天帮我检查生产异常、分析原因，并整理成报告发给生产主管。”

这句话并没有说明数据从哪里来、异常如何判断、报告依据是什么，以及通知通过什么渠道完成。产品需要把业务目标拆成可配置的能力链路：

**获取数据 → 判断异常 → 分析原因 → 形成报告 → 通知负责人**。

### 数据：先问业务流程，再识别接入方式

Master 不必先询问 API、协议或数据库，而可以问：“你们平常是怎么检查生产异常的？”

- 若企业已有业务系统或监控平台，通过数据连接器接入，并授权给数智员工。
- 若设备数据尚未进入系统，可推荐合作方的边缘采控系统先采集设备数据，再由数智员工连接该系统。具体兼容范围需按项目确认。

这种设计适应不同数字化基础的企业，而不是要求客户先完成全面改造。

### 知识：区分显性资料和隐性经验

- **显性知识**：操作手册、SOP、质量标准等。企业已有飞书、钉钉、企微文档时，可通过连接器接入；线下文档可上传至平台知识库，使用 RAG 检索。
- **隐性知识**：老师傅对异常的判断方法。通过访谈提炼经验，并在验证后转化为规则、Skill 或适当的执行流程。
- **分析与输出方法**：从既有案例提炼分析方法和报告模板，必要时沉淀为可配置的 Workflow。

不是所有知识都应直接放入 RAG。检索型资料、判断规则和固定业务流程，需要不同的产品承载方式。

### 协作：进入企业已有工作渠道

通过飞书、钉钉、企业微信或短信通知生产主管，避免要求员工为了数智员工重建沟通习惯。这里实现的是结果通知链路；是否形成包含接收、处置和异常解除的完整闭环，仍需具体场景验证。

**设计原则：数智员工应进入企业已有业务流程，而不是要求企业围绕 Agent 重建流程。**

## 05 / 设计决策三：创造可以开放，上岗需要验证，权限逐步开放

### 不以能力完整作为创造前提

即使缺少部分技能、知识或连接器，平台仍允许用户创造数智员工，并在后续逐步补齐能力。平台提供面向开源 Skill 生态的搜索与匹配；用户还可以通过自然语言创作专属 Skill，再关联给数智员工。

这降低了早期探索门槛，方便用户先用已有能力开展试用。

### 创造成功不等于生产就绪

团队通常建议企业针对数智员工的岗位职责先运行一轮 Benchmark，再投入生产环境。Benchmark 的产品化范围、自动评分能力与上线门禁机制尚待确认，因此这里将其描述为**建议流程**，而不是强制发布机制。

例如，生产异常分析助理需要验证数据读取、异常识别、分析依据、报告质量和通知对象等维度。能调用工具，不等于能正确完成工作。

### 根据业务风险分阶段使用

1. **观察与建议**：读取业务数据，形成建议和报告，不直接修改业务系统。
2. **可追溯写入**：在授权范围内产生业务记录，并标注数智员工来源，例如 CRM 客资录入和跟进记录。
3. **高风险物理控制**：如直接操作设备停机。目前未开放此类能力。

以上是产品采用的渐进式使用；第一、二阶段的具体上线覆盖与权限控制机制，需以实际版本为准。实际风险还取决于数据敏感度、可逆性和操作影响范围。

**设计原则：创造可以开放，上岗需要验证，权限应当渐进。**

## 06 / 产品化与落地

企业级 Agent 平台已正式上线，采用会员订阅模式。平台以标准化、开箱即用为目标；客户成功人员可以指导企业完成数智员工能力配置。

需要区分**平台开箱即用**与**具体业务场景无需配置**：前者不要求为每家企业重新开发平台，后者仍取决于客户现有数据、知识、系统权限与设备条件。

## 07 / 我的复盘

这个项目让我更明确地认识到，企业 Agent 产品的难点不只是模型能力，而是如何把业务目标转化为**可获得、可授权、可验证、可执行**的工作能力。

三个关键判断贯穿整个产品设计：

1. **交互层面**：让用户描述工作，而不是学习技术配置。
2. **执行层面**：让 Agent 承担理解和开放式判断，让确定性流程保障关键操作。
3. **治理层面**：降低创造门槛，但将生产使用建立在评测、授权和风险分层之上。

这套方法仍在持续迭代。未来值得继续验证的是岗位级 Benchmark 的可重复性、企业知识的可信度，以及数智员工从结果通知到真正业务闭环的能力。
