这篇文章源于企业落地 Agent 时的两个真实问题。

> 仪表老化、传感器偏移、工人操作导致的错误数据，怎么处理？

> 老师傅经验里的脏数据怎么处理？历史工单给出相反建议，AI 该听谁的？

企业有设备数据、老师傅经验和历史工单。但要让 Agent 据此判断、提出建议，得先弄清哪些能信、能信到什么程度。

读数异常，可能是设备故障，也可能是测量或操作问题。工单建议相反，可能有一张判断错了，也可能适用工况不同。接入资料，还不足以让 Agent 分清这些差别。

我更关心，企业怎样保留这些疑点，让 Agent 判断时看得到，避免检索后就当成确定事实。

下面用一个案例，把两个问题放到同一次判断里。

一台工业泵振动持续超标。Agent 查到，大部分历史工单建议继续运行、观察，少数记录了严重轴承损伤，建议立即检查甚至停机。

现场振动传感器的校准已过期，温度暂时正常。巡检员觉得声音不像轴承损伤，但证据不足以排除风险。

停机会影响交付，继续运行可能扩大损坏。Agent 要判断读数是否可靠、经验是否适用，还要考虑响应时间和执行权限。

这就是我想讨论的「可信上下文」。信息要带上来源、质量状态、适用条件和验证依据，供 Agent 判断当前任务能否使用。

## 读数有疑点，设备故障就能排除吗

传感器校准过期，读数需要核查，但未必测错；校准未过期，也不能保证读数准确。

仪表老化、传感器偏移，要排查校准、维护和测量链路；操作问题，要结合操作记录、作业步骤和现场复核，确认误操作、误录入或工况变化。不能混为一类，让 Agent 仅凭异常值猜原因。

确认测错或录错的数据，可以更正或限制使用，但要保留原始记录、原因和更正依据。无法确认的，标记待验证，不能当正常数据使用，也别直接删除，以免复盘时查不清误判原因。

传感器有问题，不等于设备没问题。确认测量链路失真，只是削弱一条证据，设备故障仍要查。

![Momo 为存疑读数标记待验证，设备故障仍需独立排查](/images/writing/articles/trusted-context/01.webp)

数据不能只有一个「可信」标签，还要说明经过什么检查、适用什么用途、有效到何时。

| 数据状态 | 含义 | 怎么处理 |
|---|---|---|
| 已验证 | 来源、口径和质量检查满足当前用途要求 | 在适用范围内用于分析 |
| 待验证 | 校准过期、来源不明，或有其他疑点 | 保留不确定性，必要时复测或核查 |
| 已确认异常 | 已确认采集链路或测量本身故障 | 不把异常读数直接当作设备真实状态 |
| 相互矛盾 | 传感器、业务系统或现场检查结果不一致 | 查找冲突来源，必要时请专家介入 |
| 已过期 | 曾经有效，但已不足以代表当前状态 | 重新获取或限制用途 |

这些状态要日常维护，不能等泵振动超标，才检查传感器是否过了校准期。

平时维护校准周期、设备档案、采集链路、数据口径、量程，以及缺失值、异常值等质量标记。异常后，Agent 先读取状态，检查数据是否过期、超出物理范围、跳变或与其他测量源冲突。

关键状态异常或证据矛盾时，再结合工况、维修记录和现场反馈深入核查，避免每次判断都从头验证。

交叉验证也要看来源。其他传感器、独立复测、负载和环境参数可以补充证据；设备型号、维护历史、近期变更，以及历史案例确认的故障和处置结果，也能辅助判断。

多个系统可能复制了同一个测量值，看似多份记录，实际只有一份证据，测错时会一起错。系统要保留来源依赖关系，不能按记录条数投票。

## 一百张工单，可能没有一百份证据

再看历史经验。

假设 100 张工单中，80 张建议继续运行，20 张建议停机检查，不能据此认定「继续运行有 80% 的支持度」。

那 80 张工单可能来自同一位老师傅，或是同一故障的重复记录。有些对应独立事件，却都在同型号、同工况下；有些只记了建议，没记是否执行、是否有效。

工单真实，建议也未必适用于眼前这台泵。

经验数据要先去重、归类、溯源。相似记录归入同一类别，便于统计频次、发现规律、识别适合标准化的问题；原始案例另行保留，记录独立事件、设备状态、工况、测量证据、处置措施、验证结果和风险后果。

问题类别保留共性，案例证据保留差异。不能把不同故障机制合并为同一种处置方案。

评估经验不能只看次数，还要看是否为独立事件，依据是现场测量、正式检测、专家判断，还是未经核实的描述，以及处置效果和最终故障原因是否确认。

再与当前现场对照。型号、负载、环境、运行状态是否相符？设备、工艺、维修标准或控制策略是否变化？误判后果多严重？是否有数量少、证据更强，却与多数建议冲突的案例？

老师傅的经验有价值，但只存「这种情况可以继续跑」，难以判断能否照做。工况、判断依据和后续运行结果要一起留下。

相反建议要放回各自现场比较。建议继续运行时，是什么型号、负载，排除了什么风险，后来是否正常？建议停机时，有什么故障证据，最终确认了什么原因？

条件不同，分别保留适用范围；条件相近仍有冲突，标记冲突，核查原始证据和最终结果。证据不足以区分时，Agent 要说明缺什么、如何复测或请谁判断，按规则升级处理，不能隐藏冲突来给出确定答案。

![Momo 对照相反工单的工况、判断依据和处置结果](/images/writing/articles/trusted-context/02.webp)

少数严重故障案例不能因数量少而忽略。经过验证，且故障机制、关键特征与当前工况相关，就应重点核查。但历史上发生过，不能证明当前也有同样故障，仍要看证据、遵循安全规则。

高频、可重复问题，可通过标准作业程序、培训、维护制度或设备改造减少；低频但后果严重的问题，需要专门的风险控制。频率和风险等级要分开看。

## 核查需要时间，现场未必等得起

先核查清楚数据和知识，再让 Agent 判断，看似稳妥。

但现场有时间要求。

工业系统有毫秒级安全保护、快速异常检测，也有按小时、天、月开展的趋势分析。检索系统、等待模型响应和人工反馈，不能成为实时安全保护的前提。

| 时间要求与任务 | 负责的机制 | Agent 适合做什么 |
|---|---|---|
| 毫秒级或严格实时的安全保护 | PLC、边缘采控、安全联锁和经过验证的控制逻辑 | 不承担必须实时完成的保护动作 |
| 快速异常检测与信号质量检查 | 边缘计算、在线监控、规则或专用算法 | 接收告警和质量状态，开展后续分析 |
| 分钟级至小时级的诊断与协调 | 设备分析系统、工单系统、Agent 协作 | 整合信息、分析原因、安排检查 |
| 日、周、月级的趋势与治理分析 | 统计分析、预测模型、Agent 分析与工作流 | 发现长期趋势、识别重复问题、推动流程改进 |

表中时间尺度只是示例，具体取决于设备、工艺和风险等级。有些在线诊断也要求严格实时，不能把设备分析都当慢任务。

回到那台泵，平时维护质量状态，异常时快速检查，可以减少等待。证据足够就分析，有疑点就收窄结论、安排核查。

复测或现场检查需要时间时，Agent 可并行分析两种情景。读数真实，可能是什么故障、优先排除哪些风险；读数失真，怎样复测、校准、检查测量链路。

两套分析都要写清前提，未核实的推测不能当诊断结论。等待期间，安全保护照常生效。停机要遵循设备保护规则、风险制度和授权流程，不能只凭 Agent 的概率判断。

## 建议被采纳了，也还没到验证结束的时候

Agent 发现的问题可能不成立，建议也可能无效。创建工单、安排巡检或完成维修后，仍要核对判断和措施效果。

全过程要留记录。从发现异常趋势、风险信号、重复问题或流程缺陷开始，Agent 给出证据、成立前提、置信程度、风险和建议动作，再按权限执行或交给授权人员决策。

现场检查、测量数据、维修记录、专家确认和运行结果，用来验证问题和建议。原始判断、执行动作、人工修改、验证证据、结果和副作用都要保留。

据此评估是否修订案例适用条件、检索策略、工作流或决策规则，再用历史回放和新案例检查效果，以及是否新增误报、漏报。

反馈不能只有「正确」「错误」，还要区分确认成立、不成立、部分成立、未验证和证据冲突。建议执行后可能效果不明，有效也可能伴随成本或副作用。

比如 Agent 提醒轴承损伤风险，企业未拆检，泵后来正常运行，不能证明提醒对错。缺少结果证据，先记为未验证。

采纳或拒绝建议不能代替结果验证。采纳率衡量使用情况，有效率要另算。

## 反复发生的问题，别只拿来训练 Agent

假设 100 次泵振动异常中，70 次是传感器安装或测量链路问题，20 次是需处理的设备故障，10 次暂未确认。

把那 70 次都算作 Agent 误报，再提高告警门槛，可能忽略了更该追查的问题，传感器为什么总装不好？

要检查安装规范、验收步骤、巡检制度、培训和设备设计，推动能减少重复问题的流程、制度整改。同时，独立评估 Agent 区分传感器异常与设备故障的能力。

流程缺陷不能全怪 Agent，判断缺陷也不能都推给现场数据。

这是复盘里我更在意的一点。有些重复问题，最终应减少对 Agent 临时判断的依赖。

比如某型号泵反复出现传感器安装松动。Agent 先归类案例，对照型号、安装方式、班组和工况，提出根因分析与整改建议；企业修订安装标准、验收流程或维护规范，再检查是否复发。

标准步骤经过验证、条件明确、执行稳定，就可写入流程或确定性规则。Agent 继续监督效果、发现例外和新问题。

![Momo 沿现场验证结果整改安装根因，并把结果记回经验](/images/writing/articles/trusted-context/04.webp)

并非所有问题都能永久消除，也并非所有经验都适合固定为规则。多种故障机制并存、工况复杂、证据不全或需跨系统权衡时，仍要动态判断。低频高危问题交给专门的风险控制机制，遵守强制保护要求。

固定规则也会过时，需要版本管理、效果验证和变更控制，不能默认过去的办法适用于以后的所有设备与工况。

## 把这些要求放回「可信上下文」

上下文需要记录的不只读数和工单，还包括来源、质量、采集条件、时间、适用范围、冲突状态、验证结果和权限约束，它们决定判断能否使用。

| 维度 | 需要弄清的事 | 对应机制 |
|---|---|---|
| 可信身份 | Agent 代表谁，职责和权限到哪里 | 身份、角色、授权范围、审计记录 |
| 可信数据 | 数据从哪里来，质量如何，现在是否有效 | 来源追溯、质量状态、时间戳、交叉验证 |
| 可信知识 | 案例是否独立、经过验证，是否适用于当前情境 | 去重归类、结果验证、适用条件、冲突管理 |
| 时效性与决策约束 | 判断必须多快完成，证据不足时如何处理 | 响应期限、超时策略、分层控制、风险升级 |
| 可信执行与反馈 | Agent 是否有权行动，结果是否验证 | 权限校验、审批、执行结果记录、评估与改进 |

这些条件不能互相担保。身份可信，数据仍可能有问题；来源真实，数据也可能过期；工单如实记录处置，建议仍可能不适合当前工况。

建议合理仍需现场验证，有效仍需执行授权。过去表现好，不能放宽安全规则；反馈进入系统后，修改模型或生产规则前仍需验证和评估。

增加上下文时，要附上来源、质量、时效、适用范围和证据等级，落实权限与安全规则。资料更多，判断未必更可靠。

## 平台该留下哪些能力

企业 Agent 平台可以从四件事做起。

一是让数据和知识有据可查。关联来源系统与原始记录，保留采集时间、更新时间、有效期、质量状态和验证依据，写清设备、工况和适用范围，记录重复、冲突或共同来源的关系，接回最终结果和验证状态。

二是让重要建议可复盘。记录当时的事实、引用案例、已确认和存疑的信息、建议成立前提，以及风险、备选方案、升级条件、最终决策人和执行动作。

保存可供审计的外部证据、判断依据和决策记录即可，不必保存或展示模型全部内部推理。

三是连接执行与结果，形成评估案例。分别看误报率、漏报率、不同故障类别表现、采纳率和有效率，并记录人工修改、专家介入、处理时间、停机时间、维护成本，以及整改后同类问题是否减少。

对照改进前后的表现，检查新风险。指标按场景定义，不能为降低误报率而显著增加严重故障漏报。

四是管理变更。知识、提示词、检索策略、决策规则或工作流因反馈调整时，记录版本、原因、评估结果和发布状态。安全规则采用独立授权与变更流程，普通反馈不能成为 Agent 自行放宽规则的依据。

## 回到开头的两个问题

**仪表老化、传感器偏移、工人操作导致的错误数据，怎么处理？**

平时维护校准、采集链路和操作记录，异常时读取质量状态，用独立测量、现场复核和工况信息补证。确认错误的数据，更正或限制用途，保留原始记录和更正依据；尚未确认的，标记待验证，限制结论强度。

分开排查测量问题和设备故障。传感器偏移不能证明设备安全，等待复测不能暂停安全保护。错误反复来自安装、操作或录入流程，就追查规范、验收、培训和维护环节，减少复发。

**老师傅经验里的脏数据，以及工单中相反的建议，AI 怎么处理？**

先去重、溯源，补齐设备、工况、判断依据和处置结果。确认错误的纠正，缺少验证的标记未验证，条件不同的相反建议分别保留适用范围。不能把少数建议直接当脏数据删除。

Agent 要比较证据独立性、来源质量、结果验证和场景匹配度，不能只数工单。经过验证的少数高危案例应重点核查。冲突未解，就说明不确定性，补证或按规则交给授权人员判断。处置后记录结果，供下次核对。

回到那台泵，建议应能查到读数是否核验、历史案例为何适用、哪些证据仍有冲突、谁有权决定下一步。检查和维修后，再补上确认的故障、处置效果和未解疑点。
