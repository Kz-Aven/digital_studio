> 制造业企业如何在不增加一线负担的前提下，收集、验证、复用老师傅的隐性经验，并形成 Agent 的可信知识闭环\

## 一、企业有数据，不代表有可信知识

制造业企业做 Agent，除了模型能力，还得看它拿到的知识靠不靠谱。

要给出可靠建议，Agent 需要**真实、适用、经过验证，而且仍然有效**的业务知识。

企业通常不缺材料。

- 设备维修工单、点检记录、质量异常单；
- 设备手册、SOP、工艺文件、检修规程；
- 交接班记录、企业 IM 讨论、培训材料；
- 老师傅在现场形成的判断经验和排障技巧。

但材料存进系统，不等于经验就能安全复用。

一张维修工单可能只写着「检查后紧固螺栓，设备恢复运行」，却漏了几件事。

- 当时出现了什么异常？
- 为什么先检查这里？
- 排除了哪些其他原因？
- 设备之后是否持续正常？

这些信息没留下，下一位维修人员即使找到工单，也未必能理解当时的判断，更难放心照着做。

这里需要分清三个层次。

1. **数据记录**，发生过什么，系统记录了什么。
2. **知识整理**，从记录和现场经验中整理出规律、条件和判断线索。
3. **可信知识**，有来源、证据和适用范围，经过相应验证，还能持续修订、撤回。

资料入库只是起点，还有一个问题要解决。

> **怎样把日常工作里的零散信息整理成可信知识，让 Agent 在合适的条件下引用，还能追踪使用效果？**

## 二、为什么老师傅的经验特别难收集？

老师傅的经验，常常体现在长期实践练出的判断力上，很难直接写成标准答案。

- 听到某种异响时，知道应该先排查哪个部位；
- 看到相似的故障现象，能根据设备型号、运行状态和最近的工况变化判断不同原因；
- 知道某个操作在哪些情况下有效，哪些情况下反而会造成二次问题；
- 能迅速排除看似合理、实际不太可能的原因。

要把这些判断留下来，有几道难关。

### 1. 经验存在于具体情境中

只记下「先检查底座螺栓」还不够，还得把这些信息说清楚。

- 什么设备、什么工况，出现了什么异常；
- 为什么先查这里，检查后发现了什么；
- 处理结果有没有得到验证。

缺了这些条件，同一句经验换到另一种设备或工况，就可能用错地方。

### 2. 访谈难以规模化

产品经理逐个访谈老师傅，既费时间，也很难覆盖大型工厂的班组、设备和特殊场景。

访谈适合深入了解少数高价值案例，但不能成为日常收集经验的唯一办法。

### 3. 额外填报会形成抵触

一线要保设备运行、处理故障、做好交接，还要完成生产任务。

每修完一次设备，再写一份「经验总结」，表单再精简，天天填也会增加负担。

### 4. 经验贡献可能被理解为岗位风险

员工可能担心，自己花多年练出的本事交给系统以后，公司会不会觉得这个岗位更容易替代？

如果只讲企业获得了多少知识，却不给贡献者直接收益，很难让人持续参与。

所以，除了录入方便，还要想清楚**什么时候问、员工能得到什么、如何保护贡献者，以及知识由谁验证和管理**。

## 三、真实案例带来的启发

下面是我找到的两个公开案例，可以帮助理解现实业务中的问题和做法，作为产品设计的参考。

### 案例一｜重庆机电智能制造｜维修完工归档与报表自动化

公开报道介绍，重庆机电集团相关企业上线设备运维智能体，连接数千台设备。

过去，维修记录靠手工填写，月底还要人工整理 Excel。上线后，维修完工可以一键归档，自动生成设备综合效率、平均故障间隔时间、配件消耗速率等指标和月度报表。

**对产品设计的启发**

1. 员工已经填过工单，就别再让他重复录入。
2. 日报、维修总结和管理报表，优先从已有工单、设备和备件数据中自动生成。
3. 先省掉重复劳动，再看哪些经验需要补充。

经验收集工具不能再添一套填报任务。能用已有数据的就直接用，缺少影响理解和判断的信息时，再请员工少补一点。

### 案例二｜博世汽车 × Poka｜现场问题管理与数字作业指导

Poka 公布的客户案例介绍，博世汽车相关工厂用其平台整合现场问题管理和数字作业指导，并对接 SAP、MES 等系统。

供应商案例还披露了问题管理、现场问题报告和作业指导创建等方面的改善数据。

**对产品设计的启发**

1. 关联现场问题、设备信息、处理过程和作业指导，减少多套系统之间的重复维护。
2. 让员工直接记录问题，留下传统工单字段之外的现场信息。
3. 记录还要经过整理、复用，才能让一个班组的经验帮助其他班组。

这个案例说明，**现场问题、企业系统和数字作业指导，可以在同一套工作流程中连起来**。

### 案例的共同启示

- 优先复用现有系统中的数据；
- 把记录动作放在原有工作流中；
- 减少重复填报和事后整理；
- 让现场信息能够进入问题分析和作业指导；
- 不把「记录数量」当成知识建设的最终成果。

每家企业是否需要独立的 AI 助手，还得先看现有系统已经能做什么。

## 四、产品定位｜AI 工友老陈

### 1. 为什么不叫「经验采集系统」？

「经验采集」「知识挖掘」「老师傅知识沉淀」这些名字，容易让员工觉得自己是被采集、被分析的对象，也会加重对岗位替代的担忧。

面向员工，我管它叫 **AI 工友老陈**，把能帮员工做什么放在前面。

**产品定位**

一线工作助手，帮员工少写材料、少重复排查、少靠记忆。工作中留下的经验，由它整理，经过验证后再用于下一次维修。

老陈是工作搭档，维修判断仍由老师傅作主。它负责这些事。

- 帮忙记下现场发生的事；
- 自动整理工单和报告；
- 找回以前处理过的相似问题；
- 把值得复用的经验整理成草稿；
- 在经过验证后，把知识提供给员工和 Agent 使用；
- 记录使用结果，帮助持续改进。

后台需要知识整理、审核、可信知识运营等模块。

员工端则要先让人感到工作方便了。一上来就要求「向公司贡献经验」，容易让人抵触。

### 2. 产品的价值顺序

1. **先让员工受益**，自动生成日报、交接班记录、异常报告，查询自己的历史工作。
2. **再降低记录成本**，工单、点检、质量异常等已有数据自动汇总，特殊信息通过语音、照片或短句补充。
3. **再让知识可复用**，AI 整理候选知识，专业人员按风险和证据要求验证。
4. **最后形成 Agent 闭环**，追踪知识是否被检索、采纳，以及是否真正改善了维修结果。

## 五、经验收集助手的设计思路

### 1. 顺着现有流程，少量补充

| 现有流程 | 触发时机 | 助手可以做什么 |
|---|---|---|
| 维修工单 | 结案时 | 自动整理维修过程；询问是否有特别的排查发现 |
| 设备点检 | 出现异常或重复异常时 | 自动关联设备与历史记录；邀请补充关键差异 |
| 质量异常单 | 处理结案时 | 汇总批次、工序、缺陷和处置；补充特殊判断 |
| 交接班 | 交班确认时 | 自动汇总未关闭问题、临时措施和风险提示 |
| 师徒带教 | 实操培训或考核后 | 记录常见错误、操作技巧和注意事项 |
| 日报与异常报告 | 提交前 | 从现有数据自动生成草稿，员工核对后提交 |
| 企业 IM | 员工主动标记或讨论关联工单时 | 在授权范围内关联讨论与问题记录 |

这些记录入口遵循三个原则。

- **已有数据不重复问。** 设备编号、工单号、备件、时间等尽量自动获取。
- **只在有价值的时刻追问。** 不要每次关闭工单都强制填写经验。
- **允许跳过。** 普通任务不需要额外总结；只有特殊、重复、高价值或高风险事件才进入深入整理。

如果使用智能工牌等产品全天候录音，或采集视频等行为数据，需要明确告知，并说明授权范围、访问权限和用途。

### 2. 采用三档记录方式

#### A. 快速补充

适合普通但值得留下的发现。

一句话、一段短语音，或者一张照片加简短说明，尽量十几秒完成。

#### B. 语音案例

适合重复故障、异常现象或值得复用的维修。员工讲清四件事。

1. 当时发生了什么；
2. 自己先检查了哪里；
3. 为什么这么判断；
4. 处理后结果怎样。

AI 把语音转成结构化草稿，只追问一个最影响判断的缺失信息。员工可以跳过，不必一次填全。

#### C. 重点事件复盘

适合重大故障、重复故障、关键工艺改进或高风险问题。

由 AI 配合现有知识专员、设备或工艺专家，整理证据、适用条件、根因假设和验证结果，也可以利用腾讯会议中的复盘记录。

完整文档的编写工作，不必都压给一线员工。

### 3. 以员工身份为中心，整合个人工作记录

通过统一员工身份，老陈可以在授权范围内关联维修工单、设备点检、质量异常、交接班、培训带教，以及与任务相关的企业 IM 记录。

把这些信息连成个人可查询的工作时间线，优先做好三类功能。

- **我的工作记录**，查询自己处理过的设备、故障、措施、结果和待办事项。

- **一键生成工作材料**，自动生成日报、维修总结、交接班记录和异常报告，员工只需核对、修正、提交。

- **我的维修助手**，按设备、故障现象或自然语言查找历史案例，并区分已验证知识与尚未确认的经验。

个人工作记录、待审核经验草稿、企业正式知识库，需要分别设置权限和生命周期。

**关联员工 ID，不代表管理层默认可以查看全部个人记录。**

### 4. AI 负责整理，不能自行认证

比如，老师傅这样描述一次维修。

> 「这台泵有时候一开机就抖，我一般先看看底座的螺栓，有一次就是这里松了。」

AI 可以整理出一张候选经验卡。

- **现象**，泵启动时出现振动；
- **排查线索**，检查底座固定状态；
- **证据来源**，老师傅原始语音、关联工单；
- **待补充条件**，设备型号、运行工况、振动特征；
- **待验证事项**，检查后是否确认螺栓松动，处理后是否持续正常；
- **状态**，待验证，不作为已确认的通用维修规范。

AI 可以转录、去重、关联设备、提取经验中的判断、发现冲突、生成追问。

但一次成功案例，还不足以让它把经验认定为正式维修标准。

### 5. 按用途和风险分层审核

建议区分四个层级。

| 层级 | 内容 | 治理方式 |
|---|---|---|
| L0 原始记录 | 工单、读数、现场照片 | 自动沉淀，保留来源与权限 |
| L1 候选知识 | AI 从工单或语音整理出的摘要、规律假设 | 自动去重、关联、标记待验证 |
| L2 已确认知识 | 有证据支持、适用范围清晰的排查线索 | 按知识用途和风险进行确认 |
| L3 高风险操作知识 | 影响人员安全、设备保护、关键工艺或质量放行的指导 | 由授权专业责任人严格审核，保留版本和变更记录 |

分层是为了避免再建一个庞大的人工审核团队。

大量重复、低价值记录，尽量交给系统处理。专业人员的时间，留给少数高价值、高风险知识。

试点时，记录每月候选知识量、人工审核时间、审核通过率、知识使用率和实际业务收益，再决定要不要设专门的知识运营岗位。

![Momo 守住审核闸门，高风险操作知识等待专业审核](/images/writing/articles/collecting-experience/05.webp)

## 六、现有维修工单已经很完整，还需要助手吗？

这是立项前必须回答的问题。

**现有系统已经能完整记录、检索、分析和复用维修知识，就别再做一套重复的助手。**

要不要做，看现有系统缺什么。不能只凭「AI 还能做更多」立项。

| 企业现状 | 应优先解决的问题 |
|---|---|
| 工单完整，但仍重复写日报、月报 | 报告自动生成与跨系统汇总 |
| 工单完整，但诊断过程和排除思路缺失 | 重点故障的轻量补充 |
| 历史工单很多，但难以找到相似案例 | 语义检索、案例关联和自然语言查询 |
| 有知识库，但知识状态、版本、证据不清晰 | 可信知识治理 |
| Agent 能检索知识，但无法追踪使用效果 | 采纳反馈、问题结果与知识版本追踪 |
| 上述能力现有系统已经具备 | 不新建独立产品，优先在现有系统中扩展 |

建议先去目标工厂，看看真实工作流程，问清几件事。

1. 老师傅完成维修后，究竟要填写哪些材料？
2. 是否在工单、Excel、微信群、交接班表中重复记录同一件事？
3. 排查类似故障时，是否需要打电话问同事或手动翻找历史工单？
4. 历史工单中的处理方法，后来有没有被其他维修人员复用？
5. 设备管理人员每月花多少时间整理维修统计和故障分析？

如果这些问题都不存在，独立助手的价值就需要重新论证。

## 七、知识使用闭环｜从「收集了多少」转向「实际产生了什么价值」

经验有没有用，要一直追到维修结果。完整流程包括以下几步。

1. 现场工作产生记录；
2. AI 整理候选知识；
3. 根据风险与证据要求进行验证；
4. Agent 在适用任务中检索并引用；
5. 员工决定是否采纳；
6. 记录执行结果和问题是否解决；
7. 发现错误或新证据后修订、降级或撤回知识。

### 建议的指标体系

| 阶段 | 指标 | 需要注意的定义 |
|---|---|---|
| 采集 | 有效沉淀率 | 具备明确内容、来源和业务上下文的候选记录占比 |
| 验证 | 审核通过率 | 已审核并通过的知识条目占已完成审核条目的比例 |
| 使用 | 知识命中率 | 有知识需求的任务中，成功检索到适用知识的比例 |
| 使用 | 用户采纳率 | 用户明确采用的建议数 ÷ 有明确采纳机会的建议数 |
| 结果 | 问题解决率 | 有证据表明问题得到解决的使用事件占可评价事件的比例 |
| 结果 | 平均维修时间 | 同类任务的处理时长变化，需考虑设备与工况差异 |
| 质量 | 知识纠错率 | 被确认错误或不适用的知识条目比例 |
| 运营 | 持续参与率 | 在观察周期内持续贡献有效记录的员工占比 |

还要看**知识未命中率**。员工频繁问同类问题，Agent 却找不到适用知识，就说明这一块需要补。

技术上，要关联知识条目 ID、版本、Agent 调用、维修任务、用户反馈和最终结果。

否则只能知道知识检索了多少次，不知道它帮助了哪次维修。

**采纳率不等于成功率。** 员工采纳了，问题却没解决，不能算有效使用。

高风险维修建议，还要单独追踪不安全建议、人工拦截和知识过期等情况。

## 八、AI 工友老陈应该解决什么问题？

**收集老师傅经验，要让日常工作中已经发生的事情，更容易记录、理解、验证和复用，尽量少让老师傅额外说、额外写。**

「AI 工友老陈」的设计应坚持以下原则。

1. **先解决员工的真实负担。** 报告自动生成、历史工作查询、交接班整理应当先于大规模知识采集。
2. **优先复用已有数据。** 不重复建设工单系统，不重复录入已经存在的信息。
3. **在自然工作流中收集。** 只在有价值的时刻轻量补充，不要求每次异常都写经验总结。
4. **AI 整理、专业人员按风险验证。** 不把所有数据都送去人工审核，也不让 AI 自行认证高风险知识。
5. **保护贡献者的信任与权益。** 明确数据用途、访问权限和贡献归属，不能承诺产品本身就能解决岗位替代问题。
6. **把 Agent 的实际使用纳入闭环。** 不只统计采集量和入库量，还要追踪知识是否被使用、是否被采纳、是否解决问题。
7. **用业务结果决定是否扩展。** 现有系统已经能做好这些事，就在原系统上扩展，避免再添一层工具。

企业需要一套能持续学习、验证和改进知识的机制，文档越堆越多还不够。

> **员工工作更轻松，经验更容易留下，知识能够被验证，Agent 能够在正确的条件下使用知识，而使用结果又能反过来改善知识。**

AI 工友老陈值不值得建，就看这些事能不能做到。
