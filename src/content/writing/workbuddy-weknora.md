很多企业并不缺文档。

设备手册、工艺文件、质量案例，还有维修记录，散落在共享盘、聊天记录和员工电脑里。真正遇到问题时，大家还是靠熟人、靠经验，或者重新翻一遍文件夹。

企业想做知识库，常常一上来就讨论平台、模型和架构。可更重要的问题是，**员工遇到一个真实问题时，能不能找到合适的资料，得到有依据的帮助？**

最近，我用 WorkBuddy 接入开源的 WeKnora，从个人公众号文章开始，再换成企业场景资料，跑了一遍从建库到问答验证的过程。

![](/images/writing/articles/workbuddy-weknora/01.webp)>

## 一、为什么选 WorkBuddy + WeKnora

### 先说 WeKnora 是什么

WeKnora 是腾讯开源的知识管理框架，面向文档理解、知识检索和 Agent 应用。它可以把文档整理进知识库，再通过检索、问答和工具调用，让 Agent 使用这些资料。

截至 2026 年 10 月 28 日，WeKnora 在 GitHub 上约有 **3.57 万颗 Star**。这个数字说明项目获得了不少关注，但不等于它已经适合每一家企业。真正的判断，还是要回到自己的资料、团队和运维条件。

### 这组搭配，降低了试点的起步门槛

我选择 WorkBuddy，是因为它已经是一个现成的 Agent 工作入口。业务人员可以直接用自然语言提问，也能查资料、生成草稿，不必先做一套新聊天界面。

我选择 WeKnora，是因为它开源，也支持本地部署。知识库可以由自己掌握部署位置、数据存储和模型接入方式，再通过 MCP 连接到 Agent。

两者的分工很直观：WeKnora 管理资料并提供检索能力，WorkBuddy 负责理解任务、调用知识和组织结果。企业可以先把这段链路跑起来，再看要不要扩展。

我看重的是**用已有工具先验证业务价值，同时保留后续调整的空间**。Agent、知识库和模型不必绑成一个整体，后面可以按企业现状替换其中一环。

### 选型时，还要把不适合的情况摆出来

| 选择                  | 更适合什么情况                              | 需要考虑什么                  |
| ------------------- | ------------------------------------ | ----------------------- |
| WorkBuddy + WeKnora | 已有 WorkBuddy，希望快速验证知识库场景；重视本地部署和自主调整 | 需要有人维护 WeKnora、模型和资料质量  |
| 采购现成知识库产品           | 希望供应商提供完整产品、服务和运维支持                  | 评估授权费用、部署边界、数据策略和后续迁移能力 |
| 自研知识平台              | 有明确的差异化流程，且具备持续研发与运维团队               | 初始投入更大，也要自行承担长期维护       |

如果企业已经有成熟的知识管理平台，未必需要再建一套。如果需求简单，现有文档系统和搜索能力也可能够用。

而对已经使用 WorkBuddy、希望从小场景试起的团队，这组搭配的好处是上手快、部署选择多，也能随着需求逐步调整。**“不受限制”不等于什么都不用管。**&#x5F00;源许可、数据合规，还有网络安全和运维能力，仍要按企业自己的要求评估。

## 二、先从个人资料验证，再考虑企业部署

![](/images/writing/articles/workbuddy-weknora/02.webp)

### 个人使用，Lite 足够起步

我先把自己写的公众号文章导入本地 WeKnora Lite。个人管理文章、笔记，或者小范围做概念验证，Lite 部署轻，能帮助我们尽快确认标题、内容和检索效果是否符合预期。

先拿自己熟悉的文章试，有一个实际好处：答案对不对，作者自己能判断。验证检索和引用的基本体验后，再决定是否扩大资料范围。

### 企业使用，按协作和维护要求部署

进入企业场景后，重点会从“能不能启动”转到“能不能持续用”。多人和跨部门的协作，长期的资料维护与权限管理，通常更适合标准化部署，再按实际需要接入数据库、文件存储、解析服务和模型。

用 Docker Compose 等方式统一部署，能让环境更容易复现。是否需要 Kubernetes，则取决于企业现有的运维体系与服务规模。不是每个试点都要一开始上集群。

还要提前确定几个责任：谁维护资料，谁处理服务故障，谁管理用户权限，备份如何做，模型和原文数据分别放在哪里。

**Lite 适合先验证，标准部署适合持续协作。**&#x4ECE;前者走向后者时，保留已经验证过的知识分类、检索问题和权限边界，迁移才有依据。

## 三、资料入库，先分类再扩展

![](/images/writing/articles/workbuddy-weknora/03.webp)

### 不要把“文件上传成功”当作知识治理完成

我这次先导入自己的 Markdown 文章，确认标题来自正文，检索结果能回到原文，再测试 Agent 能不能基于文章回答问题。

之后换成企业场景资料：设备手册、产品介绍、作业指导书，还有维修经验和质量案例。格式有 PDF 和 Markdown，结构也不一样，有上千页的手册，也有几页的经验短文。

这一批共有 9 份资料，来自公开材料，并非某一家企业完整的内部知识库。解析和索引完成后，我开始问它们能支持什么工作。这个小样本能验证搭建和使用路径，不能代表企业已经完成上线验收。

### 给资料标清楚用途和可信程度

同样是 PDF，能回答的问题可能完全不同。操作手册适合查功能和操作入口；产品介绍适合了解型号与能力；培训课件可以参考框架，却不能当成企业正式作业规范。案例文章能提供背景和数据，但也要看统计口径与适用范围。

所以，入库之前至少要弄清楚：

- 资料来自哪里，适用于哪类产品、设备或流程？
- 它是正式规范、厂商手册、案例材料，还是个人经验？
- 是否存在版本差异、重复内容和过期文件？
- 哪些内容可以直接引用，哪些只能提供排查方向？

这些信息应随着资料一起维护。否则，检索系统可能找到“相关”的内容，却没有找到“适用”的依据。

### 建立可持续更新的资料流程

企业资料不会一次性整理完。可以先约定新增、修订、失效和审核的基本流程：业务负责人确认内容，知识管理员维护版本和分类，Agent 使用时带上来源，发现缺口后回到责任人补充。

遇到资料暂时回答不了的问题，也要留下缺口记录。报警码表、切削参数、图纸公差等信息如果不在库里，就应该标记待补，不能让模型替企业编出来。

## 四、用六个问题检验知识库能否支持真实工作

![](/images/writing/articles/workbuddy-weknora/04.webp)

我把资料换成一组企业场景样本：9份设备手册、培训材料、维修经验和质量案例。六个问题从“找对资料”一路走到“生成工作成果”。结果不只是能答：它找出了资料之间的适用差异，也生成了首件检查清单和故障排查报告。复核还发现了几处不能直接照搬的判断。

### 1. 铣床系统有哪些操作手册？不同手册各自解决什么问题？

**结果：**&#x56DE;答把《铣床系统操作手册》用于操作查询，把硬件维护手册用于安装接线，把产品介绍用于了解型号。它还指出，《828D 报警手册》属于另一套数控系统，不能因为都讲机床报警就混用。它也认出了名为“作业指导书”的文件实际是培训课件，而非企业正式作业规范。

**证据意义：**&#x77E5;识库不只要搜到关键词，还要判断资料讲什么、适用于什么。否则，“相关文档”可能会被误当成“正确依据”。

### 2. 遇到某一类设备报警，应当先查哪份手册？请提供原文依据。

**结果：**&#x56DE;答根据手册章节区分了报警查看与具体代码解释。操作手册第 1.7 章说明报警、报警历史和信号查看，828D 手册第 3.2 节解释该系统的报警范围。

**边界：**&#x8FD9;批资料没有覆盖当前控制器的完整报警代码表。回答还提出按报警号格式分流，报警路由必须回到对应机型的原文核实。

### 3. 根据作业指导书，整理一份首件加工前的检查清单。

**结果：**《数控铣削作业指导书示例》共 17 个内容块，实际是一份培训课件，没有可直接执行的检查项和验收值。WorkBuddy 仍据此整理出一份 **160 行**的《首件加工前检查清单》，覆盖资料与图样、设备状态、装夹、坐标与刀具、空运行、首件检测和签核，并把待补信息列了出来。

**边界：**&#x8FD9;份清单是待审核草稿。案例里的装夹精度或平面度控制值，检查阈值仍需由图纸、工艺文件和责任人确认后填写。

### 4. 振纹问题可以从哪些方面排查？请区分资料明确记载和推测。

**结果：**《【维修经验】“振纹”问题排查方法！》列出 10 个排查方向，包括加工阶段、碰撞史、转速波动、驱动与工件刚性、丝杠支撑、刀具几何、动平衡、切削与冷却、导轨松动。原文还给出一个观察方法：切换进给方式，看表面现象是否改善，再据此排查编码器或变频器相关问题。

**边界：**&#x8FD9;是单篇、偏车削的维修经验，没有量化阈值，也不是本企业的检修规范。

### 5. 汽车零部件装配卡滞案例中，已公开的缺陷指标是什么？

**结果：**&#x56DE;答从质量案例中找到了几组数字，并区分其口径：

| 指标                | 案例中的含义                   |
| ----------------- | ------------------------ |
| 2.08%             | 基期产品装配卡滞不良率              |
| 48.5%             | 卡滞在故障类型中的占比，分母不同于产品不良率   |
| 0.52%             | 案例记录的 2023 年 6 月卡滞不良率    |
| ±0.05 mm          | 改善前记录的平面度超差量             |
| ≤0.03 mm、≤0.05 mm | 分别对应装夹/夹具高度误差和改善后的平面度控制值 |

**边界：**&#x8FD9;些是案例在特定时期的记录，不能直接当作本企业的基线或图纸验收限值。尤其“改善后控制值 ≤0.05 mm”并不等于正式验收上限，仍须核对图纸、公差和检验口径。

### 6. 请根据现有知识库，生成一份故障排查报告，并列出所有引用文档。

**结果：**&#x57;orkBuddy 生成了 **314 行、11 个章节**的《故障排查报告_数控铣床》，把设备手册、维修经验和质量案例，连同公众号里的知识治理方法，一起组织到一份报告里，并区分采用、未采用的资料。

**边界：**&#x62A5;告清单把 9 篇资料统称“直接引用”，其中一篇又标注为“已核、未引用”。公众号资料则是根据检索片段引入，并非全文核验。因此，这份报告展示了跨资料整理的能力，也暴露出引用清单需要逐条对账。它适合作为复核底稿，不能替代针对具体设备的现场诊断。

六问覆盖了资料分类、依据定位、清单整理、经验边界、数字口径和综合报告。更有价值的结果，是同时看见了知识库的能力和缺口。它能把分散资料组织成可复核的初稿，但报警码表、验收标准和现场数据仍要由业务人员补齐、确认。
