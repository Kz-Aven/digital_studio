最近我一直在想，WorkBuddy、豆包、千问这些通用 Agent 越来越好用，传统企业还有没有必要花钱找人做 AI？

一家企业想用 AI，大致有几种选择。可以找外部服务商，让 FDE（前沿部署工程师）进来调研业务、开发和部署；也可以自己组建团队，做内部 Agent 平台；还有一种更轻的方式，直接用成熟工具，安排懂业务的人做配置、系统集成和日常维护。

刚开始，我更倾向于最后一种。通用 Agent 迭代这么快，企业花几个月开发的文件处理、知识问答、数据分析功能，也许过一段时间通用工具就能做，重复建设的投入未必划算。

但再往下想，这里面还有另外两群人。一群是原来做 ERP、CRM、MES 的 SaaS 公司，它们也在给自己的产品加 Agent；另一群是 AI 应用服务商，自己不做底层模型和平台，靠帮企业梳理业务、配置工具、连接系统来收费。

如果通用 Agent 越来越强，这些公司的钱以后还能不能赚？企业自己买工具，又能不能把事情做好？

## SaaS 的 Agent，通用工具能追上吗？

假设有一家做销售管理的 SaaS 公司，原来提供 CRM、销售通话分析和报表，现在又做了一个销售 Agent，可以整理客户资料、总结通话、给出跟进建议，还能更新商机。

这当然有价值。不过我也会想，如果用 WorkBuddy 通过 MCP 连接 CRM，再配上一套销售 Skill，能不能完成其中一部分工作？即使现在做得还不够好，随着工具继续发展，差距也可能缩小。

这可能是很多 SaaS 公司会遇到的压力。过去，公司把对行业的理解做成软件功能，客户要用这些能力，就得进入它的产品。现在，一部分经验可以写进 Prompt、Skill、知识库或工作流，放到通用 Agent 上使用。原来单独收费的摘要、报表和建议，也可能逐渐变成通用工具就能提供的功能。

但连接上系统，和把业务做好，中间还隔着不少事。

比如客户要把订单从 100 件改成 150 件，Agent 能理解这句话，也能找到对应订单；可订单可能已经进了生产，库存够不够、采购要不要调整、交期会不会受影响，都得弄清楚。还要看发起修改的人有没有权限，变更后哪些系统需要同步，如果执行到一半失败，该怎么处理。

![订单变更需要检查库存、权限和生产等条件](/images/writing/articles/enterprise-ai-business/01.webp)

这些判断和操作涉及企业的正式业务状态，不能因为 Agent 能调用接口，就让它直接改数据库。权威记录可以由 SaaS 系统承载，权限、规则和审计也需要有明确的处理方式；至于最终的经营责任，通常还是由企业自己承担。

为了想清楚这些变化，我试着把企业软件的能力分成了五层。

| 层级 | 包含的能力 | 我的判断 |
| --- | --- | --- |
| 通用智能层 | 模型、推理、规划、工具调用 | 通用能力面临商品化压力 |
| Agent 执行层 | Runtime、记忆、编排、Skill、MCP | 平台之间的竞争会比较激烈 |
| 业务交互层 | 聊天界面、表单、报表、任务入口 | 部分入口可能转移到 Agent |
| 业务执行层 | 交易规则、状态变更、约束校验、审批 | 做深之后有机会形成壁垒 |
| 业务记录与责任层 | 权威数据、账务、审计、合规和责任 | 替换成本通常较高，责任仍需按实际情况划分 |

过去员工打开 CRM，查客户、填商机、看报表，很多操作都在同一个界面完成。以后员工可能直接告诉 Agent，帮我找出最近一个月没有跟进的重点客户，整理建议，再更新商机状态。Agent 通过接口调用 CRM，员工接触到 CRM 界面的机会就少了。

这对 SaaS 公司不是一个好消息。入口少了，客户对部分功能的付费意愿也可能下降；不过，后面的业务规则和正式记录还要有人维护，SaaS 能不能继续留下来，要看它除了界面和通用功能，还掌握了多少可靠、可调用的业务能力。

## 不是所有 SaaS 面临的压力都一样

简单文档处理、知识问答、内容生成这类工具，如果通用 Agent 已经能以更低成本完成相似任务，独立产品就得重新解释自己为什么值得付费。它可能被平台吸收，也可能转向更专业的场景。

CRM、采购管理、人力资源管理这些流程型产品，手里有客户数据和既有流程，但也要面对部分交互、报表和自动化能力被接管的问题。对它们来说，把业务规则、数据和操作能力开放出来，让外部 Agent 能安全调用，可能比单纯增加几个聊天入口更有用。

ERP、MES、财务和质量管理系统，涉及的业务约束、正式记录、跨系统协同更多，替换起来也麻烦，还要考虑数据迁移和经营风险。所以这类系统可能更有韧性，但也不能说只要占住底层就安全。如果产品只有简单的数据增删改查，关键业务规则都由客户自己维护，它一样可能被替换。

我也会关注 Salesforce、SAP 这类厂商接下来怎么做。它们既在原有产品中加入 Agent，也在开放接口和平台能力。对于资源有限的中小 SaaS 公司，我觉得值得先想清楚，自己的哪些业务能力能被其他 Agent 使用，而不是急着从头做一套通用平台。

## 帮企业做 AI 的服务商，能靠什么持续收费？

再看 AI 应用服务商。这类公司不一定训练模型，也不一定开发 Agent Runtime，可以基于 WorkBuddy、飞书或钉钉生态里的工具，帮助企业调研业务、整理知识库、连接 ERP 或 CRM，再培训员工、评估效果和维护系统。

我觉得这件事短期内是有需求的。工具可以买到，但一家制造企业未必知道该从采购、销售、生产还是仓储开始；也未必分得清哪些工作适合交给 Agent，哪些用普通自动化就够了，还有哪些问题得先把业务数据和流程理顺。

这和 ERP 实施有点像。企业买了软件，后面仍然需要有人协助调研、配置、迁移数据和培训员工。只是 AI 工具变化很快，今天需要服务商手工配置的东西，过一段时间平台可能就能通过对话完成。

假设一家服务商收几万元，帮客户创建 Agent、配置知识库、连接企业微信和搭建工作流；如果将来这些操作越来越简单，客户可能就不会再愿意为相同的工作付同样的费用。基础实施有机会先增长，但随着服务商增加、工具门槛下降，也可能出现价格竞争。这个过程只是我的推测，不能当作已经发生的结果。

那客户为什么还会继续付费？我觉得还是要回到具体业务。

比如服务商承诺帮助一家制造企业缩短采购订单的处理时间，从原来的两天缩短到半天，同时保证准确率和异常情况有人处理。流程有没有改善，出了问题谁来处理，投入和收益能不能算清楚。

再假设一家服务商已经做过 20 家中小制造企业的采购自动化项目。到了第 21 家，仍然要从头调研、从头开发，每多接一个项目都要增加相应的人手，那业务增长会比较依赖人力。

如果前面项目积累的系统连接、业务模板、异常处理规则和评测用例，能在新项目里继续用，交付成本逐渐降下来，质量也更稳定，情况就不同了。它可以继续做服务，也有机会把一部分经验做成产品，甚至发展成垂直 SaaS。

对服务商来说，我会关注每做完一个项目，下一次能留下什么。单纯会配置某个工具，和能够持续交付一项业务改善，客户愿意支付的费用和时间恐怕不一样。

## 企业自己做，还要面对员工愿不愿意参与

说回企业自建。我仍然觉得，一家几百人的制造企业，未必需要先招五名 AI 工程师，自己开发一套 Agent 平台。找一名懂业务、也有一定技术能力的人，使用成熟工具推动内部改造，可能更经济。

但这里有个问题，我刚开始想得比较简单了。工具好用、成本也合适，并不代表业务部门就会主动配合。

假设一个车间班组有四个人，每天工作八小时，某项原本需要八小时完成的工作，用 AI 一个小时就处理完了。单看这项工作，处理速度提高了八倍；可企业的订单、设备产能和业务量不一定跟着增加。省下来的时间怎么安排，员工并不知道，老板可能让大家承担更多工作，也可能考虑减少岗位。

如果我是负责这项工作的员工，也会担心，把自己积累的经验都教给 AI 之后，工作会发生什么变化。

![效率提升与员工对工作变化的顾虑](/images/writing/articles/enterprise-ai-business/02.webp)

这里有点像经济学里说的棘轮效应。员工展示了更高的工作效率，管理者可能把它变成下一轮的考核标准，员工就未必愿意充分展示自己的能力。AI 让这种担心更直接了，尤其当一些任务的效率提升很大时，最了解业务、最能帮助企业改造的人，也可能是最担心岗位变化的人。

所以，企业想让业务部门参与，得把效率提高之后的安排讲清楚。省下来的时间能不能减少加班、降低工作强度？员工有没有奖金、培训、转岗或者晋升的机会？如果这些问题没有答案，只说让大家一起提效，实际推进时遇到抵触也不奇怪。

当然，也不是每家企业都能承诺不裁员。有的企业经营本来就困难，引入 AI 的目的之一就是降低人工成本。这种情况下，管理层需要面对的就是岗位调整，以及培训、转岗和补偿等问题，不能只把它包装成给员工减负。

经营负责人先明确目标和预算，少量内部 AI 应用人员负责工具选型、系统连接、流程分析和效果评估，业务部门提供专业知识并参与验证；管理层同时把收益分配和岗位安排考虑进去。

企业需要知道自己要改什么、数据和业务规则由谁控制、结果如何验收，但不一定要把模型、平台和所有实施能力都自己做一遍。成熟工具可以采购，外部服务也可以用，关键业务的决定权还是留在企业手里。

## 做出了价值，能不能把钱赚回来？

想了一圈，我对最初那个问题的看法也变了。通用 Agent 越来越强，不代表传统 SaaS、AI 服务商和企业内部团队只能留下一种。它们可能继续分工，也可能进入彼此的领域。

通用平台提供模型、执行和交互能力；SaaS 维护业务系统、交易规则和记录；服务商帮企业连接系统、改造流程；企业自己确定经营目标，掌握业务规则和最终决策。实际合作时，SaaS 也可能自己做实施，服务商可能做成软件产品，企业也可能培养团队，逐步减少对外部人员的依赖。

但能把事情做好，和能从中获得多少收益，还需要分开看。

一家 SaaS 公司提供的业务系统可能不可缺少，但如果员工的入口转到了通用 Agent，原有功能也面临竞争，它仍然可能承受定价压力。服务商完成了复杂改造，如果每个项目都高度依赖人力，也未必能把业务做大。

企业自己使用 AI 也是一样。某项任务从八小时缩短到一小时，并不意味着企业利润会提高八倍。假如真正限制交付的是物料供应、设备产能或者订单量，这项工作的提速能带来的经营收益就可能有限。省下来的时间和成本如何分配，也会影响改造能否继续推进。

![节省时间需要经过业务瓶颈才能转化为利润](/images/writing/articles/enterprise-ai-business/03.webp)

所以回到标题，我觉得传统 SaaS 要看自己有没有难以替代的业务能力；AI 服务商要看能否持续解决客户问题，并让经验在下一次交付中派上用场；传统企业则要想清楚，AI 改完之后，效率到底能转化成多少经营收益。

这几件事都不容易。Agent 的能力越来越普及是好事，至少企业可以用更低的门槛尝试一些过去做不了的事；但买来工具之后，业务怎么改、员工怎么参与、收益怎么算，还是得一件件去解决。
