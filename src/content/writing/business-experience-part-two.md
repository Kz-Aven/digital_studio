> Agent 说「录入成功」，跟进却写进了别人家客户

那天上午八点，我让销售助理阿单给大东科技录两条拜访跟进。

八点零七分，它回了：跟进已录入成功，客户是广州大东科技有限公司。

语气、格式、客户名，全对。我差点就往下走了。

后来核对数据库才发现，这两条记录实际挂在宏远五金下面。

这是这个项目里最值钱的一次失败。它把我原来的验收标准直接推翻了：我先前只看「调用成功没成功」，之后得问——用户说的、系统写的、屏幕上显示的，是不是同一个东西。

上篇写客户、掉保规则和只读 MCP。这一篇从多对象讲起，一直走到 AI 员工实测和这次错绑的修复。

## 01 对象要加，关系要克制

只有客户一个对象的时候，很容易偷懒：所有销售推进都塞进「客户跟进状态」里。

可一个合作三年的老客户忽然又冒出增购机会，一个状态字段说不清这两件事——原来那单还在履约，新的这单才刚起步。

所以后来补了线索、联系人、商机、合同、订单、跟进记录，客户也分成企业和个人两类。

![围绕客户的多对象关系](/images/writing/articles/business-experience-part-two/01.webp)

在这套业务里，商机、合同、订单的上游主体都是客户。商机和合同之间、商机和订单之间，没有默认的直接关联；订单可以选配同一客户的某份合同。

如果为了把 L2C 图凑得好看，硬连成「商机生成合同、合同生成订单」，后面所有统计和自动化就建在了一条不存在的关系上。

几个容易混的地方：线索是信息还没补全的东西，转不转客户通常由销售判断；客户是往来主体，分企业和个人；联系人是具体对接的那个人，独立记录、挂在一个客户下；商机是一次可能成交的机会，同一个客户可以有好几条；合同和订单各管自己的事实和推进状态。

我用 L2C 组织这些关系，但范围没覆盖完整回款、应收和履约。

## 02 关系之外，状态得拆开

商机阶段由企业统一配，每个阶段对应一个赢单概率。销售可以手动推进，也可以回退。赢单不由客户关联的某张订单倒推出来。

原因很实际：一个客户挂着好几条商机、几份合同和订单，光看客户，你没法确定到底是哪一条赢了。

客户成交状态、商机赢单、合同归档，各有各的语义。名字像，不等于能互相顶替。

权限也是一样。一个人是某条商机的协作人，他能看这条商机，但不会因此拿到关联客户的全部权限。

实测时我专门问过一句：「为什么 商机O003 能看，客户C010 不能看？」服务端按对象分别处理，答得出来。

**有关系，不等于有权限。** 这些边界得跟着本体一起落到工具里，不能只写在文档上。

## 03 写工具之后，责任变了

只读阶段，Agent 主要是查和解释。加了写工具，每一次调用都可能动到归属、阶段，或者一条业务记录。

我先把七类表单的新增补齐，再做编辑和软删除，然后是转客户、领取、回收、分配、待办这些业务动作。

![普通录入与业务动作共用受控执行层](/images/writing/articles/business-experience-part-two/02.webp)

普通表单写入查字段和关联；业务动作还得查当前状态、容量、冷静期、规则和影响范围。

比如「刷新客户预计掉保时间」，不能当成批量改一个时间字段。它可能让客户当场到期，得先给影响预览，确认了再执行。

总容量和领取频次也是两回事：手里能压多少客户，和一天能领几次，是两种约束，配错了照样出事。

| 写入时会碰到 | 怎么处理 |
| --- | --- |
| 必填信息缺失 | 返回缺哪几项，让 Agent 用业务话去追问 |
| 系统能定的默认值 | 自动填，比如新询盘、订单折扣默认 1 |
| 重复请求、旧版本编辑 | 幂等键加版本检查，防重复也防覆盖 |
| 删客户 | 底层记录留着，客户和相关记录退出读取和统计 |
| 平台订单、聊天同步记录 | 字段不许随便改，保住来源的真实性 |

对象负责人默认拥有这个对象的全部权限。

这些检查都在服务端做。不能指望模型每次都记得。

## 04 交给AI 员工阿单真实跑

MCP 接进 tigerose 之后，「销售助理阿单」开始接真任务：查客户、改阶段、建商机、录线索、转客户。

这一步能照出脚本测试看不到的东西：用户到底怎么说话、Agent 会不会追问、失败之后怎么爬回来，以及最后怎么跟人说结果。

有个顺利的例子。展会线索转企业客户，线索里有张总，没有公司名。

![阿单追问缺失企业名称，并在补充后继续转换](/images/writing/articles/business-experience-part-two/03.webp)

*从 tigerose 历史会话采集。截图保留了当时的问法和候选项，呈现的是补全信息的过程。*

阿单读了转换要求，回头问我企业名称。我给了公司名，它接着转完，还补建了联系人把联系方式存进去。

到这儿看着挺顺。但一个顺利的任务，证明不了这套东西可靠。

很快，跟进录入给了另一种答案。

## 05 名字对了，归属错了

历史回复里有这么一行：

> 客户：广州大东科技有限公司（C001）

大东是我指定的客户。可 C001 在库里对应的是宏远五金。

![历史回复中的客户名称与 ID 不一致](/images/writing/articles/business-experience-part-two/04.webp)

*从 tigerose 原始会话采集，画面下方保留了「大东科技（C001）」这处矛盾。*

对用户来说，名字对、提示是成功，几乎不可能再去怀疑。

可总不能让用户背住每家的 ID，一条条对。

我让系统直接查库，三路交叉：活动原记录、关联客户后的有效查询结果、保存下来的创建回执。三处一致——两条刘总的拜访记录，都写在宏远五金下面。

**这是已经发生的业务关联错误。** 后面就算正式把大东的客户阶段改对，这两条错绑的跟进也不会自己回来。

## 06 校验要对齐的是「用户指的那一个」

这件事不能简单记成「数据库没校验」。

传进来的客户 ID 存在，当前员工也有权限，外键和常规鉴权都可能顺顺当当通过。

缺的那一问是：这次被操作的客户，是不是用户指的那一个。

当时没有完整捕获每一步的原始模型参数，所以我没法只凭最终回复断言错误出在哪个环节。但缺口是清楚的：写入链路没有把「用户说的大东」和「服务实际写进去的对象」可靠地绑在一起。

![目标绑定、落库回读与可信回执](/images/writing/articles/business-experience-part-two/05.webp)

修复拆成三块。

先按客户名称定位目标。名字唯一就往下走；有歧义就请用户按业务信息选一个，由服务生成一个绑定当前员工、任务和操作的目标引用。

再在事务里校验这个目标，写完之后重新读一遍实际关联。哪怕写入函数返回的结果看着很对，只要落库后的关联不一致，就回滚。

最后返回服务端生成的真实回执：实际客户名称、内容、时间，再配一个回执复核工具。

这比在提示词里加一句「注意别写错客户」，多了一道能执行的检查。

还剩一个边界：如果模型连查名称都传错了，而宿主没有把原始用户意图绑住，MCP 单独没法证明用户最初指的是谁。

所以宿主应该从可信的工具通道取回执，绑上原始任务目标再展示，而不是让模型自己重写一份「成功结果」。

## 07 改数据，也留证据

两条错绑的记录已经更正到大东名下。

更正保留了原文、发生时间和作者，没有删掉重建，没有把它包装成一次新的客户沟通，也没有因此续保。

原来的错误关联和旧创建回执继续留着做历史，另外追加更正记录和审计事件。业务查询读的是更正后的有效视图。

这样既纠正了当前结果，也留着「发生过什么、为什么修、修成什么」。

直接覆盖历史最省事。可那样以后排查，只能看到一个正确结果，永远不知道当初错在哪。

## 08 评估得分四层看

我把任务执行链和数据库事件放在一起对，慢慢分出四个层次。

| 层次 | 要查什么 |
| --- | --- |
| 调用层 | 工具调没调，协议通不通 |
| 业务层 | 是写入成功、拒绝、等补充，还是幂等返回 |
| 数据层 | 对象、关联、时间、状态写对没写对 |
| 展示层 | 用户看到的结论，和实际结果是不是一回事 |

工具调用成功只说明协议通了，说明不了业务有没有动，更说明不了动的是不是你要的那一行。

评估还得有人在里面。执行链里有「预览 8 条、实际刷新 7 条」和「代拟跟进」两处看着可疑，我确认过是有授权的，就不该继续判成越权。

同样，多次工具调用不能算成多次独立写入；任务恢复前后的片段，也不能算成两个任务。

现在项目里有 8 组独立的 Agent 验收场景，外部执行记录只覆盖了一部分。工程侧有 132 项单元测试、六组 STDIO 协议合计 303 次调用通过，写入回归跑在隔离库上。

这些数字说明工程检查铺到了哪里，换算不出 Agent 自主任务的准确率。

![从业务经验到评估反馈的闭环](/images/writing/articles/business-experience-part-two/06.webp)

## 09 两篇走完，剩下什么

到这里整条路才闭合：经验被拆成资产，经 MCP 进到 Agent；真实任务把错误撞出来，错误再变成校验和回归用例。

这一轮还补了检索、指标、分级、线索公海、分配、配置版本和待办。

从 CRM 挪到别的领域，同样要当心：供应商名字看着对，订单、物料、履约对象也可能挂错。

我现在养成了一个习惯，看完 Agent 的回答，还要去核它真正改掉的业务事实，确认这两者说的是同一件事。

你那边有没有一种「看着成功、其实写错了」的结果，是你最想提前拦住的？我想听听，因为我发现这类错误几乎都不出现在报错里。

我们称之为 **「水下的问题」**。
