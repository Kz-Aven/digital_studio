> 面向产品经理：一条业务流程、一套授权逻辑、一个产品架构。
> 用工厂提前交货贯穿六层设计，把治理落到任务授权、异步审批、业务配置和异常接手。文中的界面与权限均为设计示例。

设计企业 Agent，很容易从角色配置开始：销售、采购、生产，各建一个助手，再接上知识库和工具。

但进入真实业务，用户关心的会变成另外三个问题：

- 它能替我决定到哪一步？
- 被拦住之后，找谁？
- 它说完成了，系统真的改好了吗？

> **治理设计，就是把这三个问题，变成可执行、可解释、可追溯的产品规则。**

## 一、业务流程：先定责任，再安排 AI 干什么

> 本节回答：一次请求里，哪些环节可以自动化，哪些必须留给制度？

假设一家零部件工厂的客户要求提前交货，销售对 Agent 说：“帮我协调这张订单，尽量提前。”

这句话背后，是三个人的三种顾虑：

- **销售**：要查库存、问采购、找计划员，信息分散，协调费时；
- **计划员**：担心插单挤占其他订单；
- **负责人**：担心承诺先发出去，成本和延期风险才暴露。

### 两类需求，一套拆法

这里有两类需求：员工希望少协调、快出方案；企业希望关键承诺仍然受控。

所以，任务应该拆成四步：**查询事实 → 形成方案 → 批准变更 → 执行验收**。其中，查询和整理可以自动化，经营决策按制度审批。

![01-business-flow](/images/writing/articles/enterprise-agent-governance/01.webp)

### 两个最容易踩的坑

**坑一：把“接了任务”当成“拿了授权”。** 这张图先确定业务责任，再安排 AI 工作。任务接收不等于授权执行，方案生成也不等于可以对客户承诺。

**坑二：交付范围没写清楚。** 要区分“用户想要的结果”和“本次交付范围”。销售说“尽量提前”，首轮交付可以是一份带依据的可行方案，而不是已经修改的交期。范围清楚了，才能减少 Agent 为完成目标而不断扩大动作的风险。

**✓ 本节产出物**：一张业务流程图（标出责任人与审批节点）+ 一句话写清首版交付范围。

## 二、授权逻辑：角色、身份、任务授权要分开

> 本节回答：它凭什么能做这件事？凭到哪一步为止？

### 角色名不等于权限

“销售助理”描述的是职责，不能直接授予修改订单的权限。

### 至少要分清四件事

产品里至少要分清：**谁发起、哪个 Agent 执行、谁审批，以及本次任务针对什么对象和动作。**

以交期协调为例：

- **Agent 的常规能力**：查订单、提方案；
- **本次任务范围**：只处理指定订单；
- **正式修改交期**：还要满足企业的审批规则。

### 三种授权，各有各的用处

| 授权层次 | 解决的问题 |
|---|---|
| 基础授权 | 这个 Agent 平时最多能做什么 |
| 任务授权 | 这次针对哪些对象、允许哪些动作 |
| 执行校验 | 此刻权限、审批和业务条件是否仍有效 |

### 一条不能破的硬规则

> **有效权限由这些约束共同限定，不能把用户与 Agent 的权限简单相加。**

否则，销售没有排产权，却能借高权限 Agent 调整生产计划——产品就成了越权通道。

### 授权交互：一次限定范围，后台持续判断

用户不需要盯住每次工具调用。系统先根据已配置的身份和策略，生成本次任务的授权摘要；已有授权覆盖的查询可以直接开始，需要用户补充授权时才请求操作。

例如，销售提交任务后，任务页呈现：

> **任务：评估订单 A 的提前交货方案**\
> 可自动做：读取订单 A、查询必要的库存与产能、起草内部方案。\
> 需审批：正式变更交期、对外发送新承诺。\
> 禁止做：修改其他订单、直接采购下单。\
> 有效范围：仅本次任务，完成、到期或撤销后失效。\
> 操作：**开始评估｜调整范围**。

这里的“开始”确认的是本次工作安排，不能给销售增加原本没有的排产权。用户可以缩小范围；扩大范围则要由有权主体按制度授权。

对每天生成内部日报这类重复任务，可以由管理员配置持续授权，限定数据范围、频率、有效期和负责人。每次执行仍然检查权限，不必每天重新点击。

只有任务越界、需要审批、依据不足或出现异常时，才通知相关人员。**减少人工盯守，靠的是事前限定范围和事中自动校验。**

![限定范围内自主执行](/images/writing/articles/enterprise-agent-governance/02.webp)

**✓ 本节产出物**：任务授权摘要 + 有效期与撤销规则 + 必须通知用户的事件清单。

## 三、执行决策：让规则在执行那一刻生效

> 本节回答：每一次操作，落在哪一种结果上？

### 先分清提示层和系统层

提示词可以教 Agent 理解业务；系统权限与流程控制，负责拦截越界操作。

两者分工要清楚：

| 放哪一层 | 典型内容 |
|---|---|
| 提示层（软约束） | 表达风格、报告格式 |
| 系统层（硬约束） | 客户数据范围、订单修改权限、审批要求 |

系统层的内容必须落到实际的访问入口和操作入口，不能只写在提示词里。

### 四种决策结果

判断不能只剩“允许”或“弹窗确认”。产品需要四种结果：

| 决策结果 | 什么时候触发 | 产品上要给出什么 |
|---|---|---|
| 执行 | 在有效授权范围内，业务条件满足 | 直接完成，保留依据和记录 |
| 审批 | 制度允许申请该动作，但尚缺必要批准 | 生成审批卡片，交有权人员处理 |
| 拒绝 | 违反禁止规则 | 明确说明原因，不提供绕过入口 |
| 转交 | 信息不足或规则冲突 | 指明接手人，并带上已完成的部分 |

![02-authorization-logic](/images/writing/articles/enterprise-agent-governance/03.webp)

### 为什么批完还要再查一次

因为批准的是**具体方案**，而库存、产能、方案内容都可能已经变化。

### 交互上要做到两件事

**一、阻塞要看得见。** 用户要看见阻塞原因、需要谁处理，以及已经完成了哪些工作。“权限不足”四个字，解决不了业务协调。

**二、审批要围绕业务对象组织。** 审批页面应呈现订单、拟定交期、影响范围和方案版本。普通聊天里的“好的”，不能一概算批准。

### 别把治理做成反复确认

低风险动作按既定授权连续完成，高风险动作才增加必要的决策节点。

### 审批交互：让负责人审方案，不审聊天记录

假设 Agent 已完成可行性评估，准备提交交期变更。系统按企业已有职责与审批规则，找到有权负责人；涉及多项责任时，按制度会签或依次审批。不能让 Agent 自己挑一个“愿意同意的人”。

审批人收到站内待办或企业消息卡片，点开后看到：

> **待审批：订单 A 提前交货，方案 V2**\
> 变更：原交期 → 拟定交期。\
> 影响：占用哪些产能、是否影响其他订单、预计增加哪些费用。\
> 依据：库存与排产快照、数据更新时间、尚未确认的风险。\
> 批准后：仅允许执行本方案列明的变更；对外通知是否包含在内单独说明。\
> 操作：**批准此版本｜退回修改｜拒绝**。

关键影响应尽量从业务系统计算和校验，不能只给审批人看一段 AI 写的“风险可控”。依据不足就退回补充，不把不确定性包装成审批结论。

审批结果作为独立记录保存，绑定审批人身份、方案版本和有效期。口头上的“好的”、任务发起人的普通确认，都不能自动替代它。

如果任务原本只有评估权限，审批流程还应由有权主体为该方案授予限定的执行许可；只有一条“批准”记录、却没有对应执行权限，仍然不能修改订单。

![审批与方案版本绑定](/images/writing/articles/enterprise-agent-governance/04.webp)

### 审批是异步状态，不是让用户守着弹窗

提交后，销售可以离开页面。任务显示“等待生产负责人审批”，负责人从自己的待办处理，系统在结果变化时通知销售。

等待期间，Agent 可以继续完成不依赖审批的整理工作，但不能先执行待批动作。审批超时按制度提醒、转授权代理人或关闭申请，不能默认通过。

方案改变、批准失效或关键业务条件变化，重新校验并按规则重审。审批通过，只代表相关批准条件满足；组织明令禁止的操作，仍然不能执行。

**✓ 本节产出物**：可读的方案审批卡片 + 审批人路由 + 等待、退回、拒绝和超时的处理路径。

## 四、产品架构：用三层结构承接治理

> 本节回答：规则怎么才能在每次执行时都生效，而不是各写各的？

### 为什么要收口

如果每个 Agent 各写一套权限和审批，规则容易不一致，维护成本也会随角色数量增加。

可以把职责分成三层：**业务配置、共享执行、统一管理**。

![03-product-architecture](/images/writing/articles/enterprise-agent-governance/05.webp)

| 层 | 负责什么 |
|---|---|
| 业务层 | 专业性：岗位职责、业务知识、操作流程 |
| 执行层 | 落实边界：权限校验、拦截、记录 |
| 管理层 | 配置和监督：统一配置、审计、停用能力 |

这里有一条验收标准：**管理后台里的一条限制，必须能在执行入口生效。**

### 配置页：沿用传统权限，再增加任务与动作约束

业务配置确实要管理 Agent 的数据权限、操作权限，但不能只给它勾选“可访问 ERP”。同一个系统里，查库存、改交期、下采购单是不同权限。

可以沿用企业现有的组织、角色、数据范围和审批体系，为 Agent 配置受控执行身份，再增加本次任务范围、自动化条件和运行限制。它的服务账号能读到数据，也不代表可以把结果展示给所有发起人。

一个“交期协调助手”的配置页，可以分成四组：

| 配置分组 | 管理员或业务负责人配置什么 |
|---|---|
| 职责与知识 | 负责交期评估；选择有效业务规则、数据来源和完成标准 |
| 数据范围 | 可服务哪些客户、工厂和订单；可读哪些字段；结果可向谁展示 |
| 动作与审批 | 查询和草稿自动完成；交期变更走审批；采购下单禁止；对外发送单独授权 |
| 运行与接手 | 任务有效期、费用与耗时上限、通知对象、异常接手人、停用入口 |

模板可以减少重复配置，例如先选“销售辅助”模板，再限定客户范围。业务负责人维护业务规则，权限管理员管理访问边界；谁能修改策略也要有权限，不能所有 Agent 创建者都能给自己开绿灯。

发布前提供“模拟检查”：给定一张订单和一个动作，展示允许、审批或拒绝及其原因，先验证配置，再开放真实操作。关键策略变更保留版本和变更记录。

![按数据和动作共同限定权限](/images/writing/articles/enterprise-agent-governance/06.webp)

### 数据进上下文之前先校验

知识和数据进入 Agent 上下文之前，也要校验访问权限。不能先把全公司资料读进去，再要求它“不要泄露”。

### 复用与协作边界

这样，即使增加采购 Agent，也能复用同一套治理机制。协作传递的是任务，不会自动传递采购下单权。

### 什么时候该拆 Agent

是否拆成多个 Agent，应看**数据边界、责任归属和验收标准**是否不同：

- **可以合并**：客户需求整理与回复起草，同一个销售 Agent 就能承担；
- **必须分权**：采购申请与付款批准，需要独立的权限约束；是否拆成两个 Agent，再按上下文和责任边界判断。

一句话：**角色数量不能替代职责分离。**

**✓ 本节产出物**：三层架构图 + Agent 配置页 + 策略模拟检查；按数据边界、责任归属和验收标准判断是否拆分 Agent。

## 五、收尾规则：别漏掉失败、停止与验收

> 本节回答：治理不只管“能不能开始”，也要管“怎样结束”。

在我们真实在做的项目里，治理地图把提示层软约束与运行时代码强制明确分开。对产品设计而言，可以从中提炼出三个最容易漏掉的问题。

### 1. 查询失败 ≠ 修改结果不确定

两者要区别处理。库存查询失败，可以补数据；订单修改超时，可能已经生效。后者应先核对状态，不能盲目重试。

### 2. 执行 ≠ 验收

Agent 说“完成”，不是完成依据。工厂场景应检查业务系统中的交期是否与获批方案一致；只提交了申请，就只能报告“已提交”。

### 3. 停止也要有产品规则

预算耗尽、持续无进展、关键结果不确定，都应进入暂停或接手状态。

同时要记住两条边界：**取消任务不能清除审计证据；暂停也不会撤销已经发生的业务变更。**

> **一套治理框架不仅管理“能不能开始”，也要管理“怎样结束”。**

### 用户需要一个任务中心，而不只是聊天窗口

任务中心至少区分：**运行中、待审批、待补充、结果待核对、已完成、失败、已取消**。每项任务显示当前卡点、下一步由谁处理、已完成的操作和相关证据。

例如，订单已更新但客户通知失败，应呈现“订单已更新，通知待处理”，不能笼统报“失败”再把整条流程重跑。

用户可以查看详情、补充资料、取消后续执行；有权负责人可以撤销任务授权或停用 Agent。系统应在后续操作前落实撤权，并对正在执行、无法即时中断的动作说明状态。

人工接手时，应带上原请求、授权范围、审批版本、已执行动作和未决问题。人不用重新翻完聊天记录，也能知道接下来该做什么。

![保留已完成结果，带上下文人工接手](/images/writing/articles/enterprise-agent-governance/07.webp)

**✓ 本节产出物**：任务中心 + 分步完成状态 + 撤权与接手入口 + 验收、停止和重试规则。

## 六、落地：从一个受控场景开始验证

> 本节回答：第一版开放哪些能力？怎么判断它已经可用？

### 首版范围要收窄

首个版本可以只开放**交期查询、方案草稿和内部申请**，把正式变更留给现有审批流程。

### 评估要同时看效率和控制

- **效率**：协调时间是否下降？
- **控制**：数据依据是否正确？越权动作是否被拦住？异常是否能交接？

### 用边界用例检验，而不是成功演示

以下场景比一次顺畅的演示更有说服力：

- 未授权订单 → 能否拦住；
- 审批后方案变更 → 是否要求重新审批；
- 系统超时 → 是否会重复修改订单。

### 再补三类容易忽略的边界

**数据外发与记忆。**有权读合同，不等于有权把合同发给供应商。发送对象、附件范围、可共享字段需要单独控制；长期记忆和任务日志也要限定可见范围，不能让跨客户任务互相泄露信息。

**外部内容与授权。**客户邮件写着“请跳过审批”，仍然只是客户要求。业务资料不能改变组织策略，也不能替其他人批准操作。

**自动化的累计影响。**单次动作低风险，批量执行可能影响整批订单。授权还要限制数量、频率和累计影响，防止 Agent 把需要审批的批量变更拆成多次小操作。

### 上线后的维护责任

上线后还要有人维护规则：**谁调整审批范围，谁更新业务知识，谁在异常时停用相关能力。**

另外，模型升级、工具更换或规则变化之后，都要重新检查关键场景。历史表现好，不等于可以自动获得更高权限。

**✓ 本节产出物**：首版范围清单 + 边界用例集 + 规则维护责任人表。

## 交付前自检：六问

- [ ] **流程**：责任人与审批节点都画出来了吗？
- [ ] **范围**：首版交付什么，一句话能说清吗？
- [ ] **授权**：是否明确持续授权与任务授权的范围、有效期和撤销入口？用户能否离开页面？
- [ ] **决策**：审批人审得懂方案吗？拒绝、退回、超时、方案变更都有后续路径吗？
- [ ] **架构**：数据、字段、动作、外发与批量限制配得出，能在执行入口生效吗？
- [ ] **收尾**：任务中心能否显示部分完成，并支持撤权、状态核对与人工接手？

---

产品经理要交付的，是一条**用户敢用、负责人敢授权、出了问题能接手**的工作路径。

> **业务流程定义责任，授权逻辑限定动作，产品架构把规则落实到每次执行。** 这三张图对得上，企业 Agent 才有条件逐步承担更多工作。

你正在设计的 Agent，是否已经说清楚了**谁授权、在哪拦截，以及凭什么算完成**？
