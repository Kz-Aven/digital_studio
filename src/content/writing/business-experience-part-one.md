> 把 CRM 拆成 Agent 能读懂的资产，我先从掉保规则下手

销售的原话是：「帮我把今天的跟进排一下。」

这句话我听了很多年。可真要排出来，得先知道他手上都是谁、上次聊到哪一步、哪几个有戏，以及还有几天这些客户会被系统收回去。

我在 SaaS 和 AI 应用上做了多年，也带过 CRM 和手机的项目。这套业务我熟得能背——问题恰好在这儿：它只在我脑子里、在几个老销售的肌肉记忆里、在代码的 if-else 里。Agent 一样都读不到。

所以我想把它拆出来，做成 Agent 能调用、也能被检查的东西。

入口挑得很具体：「客户」和「掉保规则」。这一步走通了才敢往下走，多对象、写入、实测。

## 01 先划一条边界

我一开始就没打算「做一个 CRM」，太重（主要是 CRM 对于几乎绝大部分企业都是现成的）。我问自己的是：Agent 要在这套业务里给出一次靠谱的回答，最少需要哪些东西。

最后落成五类。

![五类业务资产](/images/writing/articles/business-experience-part-one/01.webp)

- 本体说清有哪些对象、彼此什么关系；

- 状态机管对象怎么变；

- 规则管什么条件下能做什么；

- 工具是执行的入口；

- 评估用例用来判断结果对不对。

五样东西凑成一个语义层。验收标准我定得很窄：一个熟这套规则的人，和一个调工具的 Agent，对着同一个业务问题，能不能给出同一个解释。

有人建议过最省事的做法——把建表语句直接扔给模型可以吗？

不行！字段解释不了取舍。

「预计掉保时间」在表里就是个时间字段。可它背后压着：客户归属怎么算、什么算有效跟进、两条规则冲突听谁的、管理员改了规则要不要重算。这些没有一条在字段里。

## 02 客户身上挂着两套状态

CRM 里「掉保」是说：清空负责人，客户回到指定公海；原负责人还可能进冷静期，几天之内不能重新领。

一件事牵出五个东西——客户、员工、公海、跟进动作，还有一份保护快照。

![客户与客保的核心关系](/images/writing/articles/business-experience-part-one/02.webp)

麻烦在同一个客户身上挂着两套状态。一套是销售推进到哪了：初步接触、报价、谈判。另一套是归属和保护：在谁手上、什么时候到期、有没有被锁住。

这两套经常被混着说。客户正在「报价」，不代表他这周不会掉；客户进了公海，也不代表之前的跟进该消失。

拆开之后，Agent 才可能说清两件不同的事：这个客户值得跟；这个客户为什么快掉了。这两句话的答案，很多时候并不一致。

## 03 规则不难，难的是规则打架时听谁的

掉保规则最初看着特别简单：拿到客户，N 天没跟进，释放。

真跑起来，老板们的诉求是反的。有的要让销售别拖，三天不动就收走；有的怕销售随手写一行字，把客户锁死半年。

插一段原来的经验。我之前那个手机项目能同步真实沟通记录，还能自动生成跟进总结。把这批有来源的数据接进 CRM，改动很小，效果却比预期好：销售少填一遍表，管理者看到的也不再是「打了个电话，客户说再看看」这种谁都能写的话。

所以「什么算有效跟进」必须可配。手工备注、改状态、聊天总结、平台订单，是不同的动作类型，由管理员决定哪些能延长保护期。

这里有个容易漏的点：**记录保存成功，和续保成功，是两个不同的结果。**

| 会遇到的情况 | 决策定下的口径 |
| --- | --- |
| 多条规则同时命中 | 取最晚的掉保期限 |
| 最晚期限并列，后置动作不同 | 看最近编辑的那条规则 |
| 历史跟进算不算一直有效 | 记录都留着，计算只认本次持有期间、当前负责人的有效动作 |
| 管理员改了客户规则 | 存量快照不动，靠一次明确的刷新动作重算 |

取最晚的期限，是因为早点释放虽然流转快，但销售撞单和归属扯皮也跟着来。这个取舍是被管理成本逼出来的，不是技术选择。

把原因一起写下来，Agent 才解释得了规则。只给结果，它只会说「系统就是这样」。

## 04 「预计掉保时间」这六个字

规则定完，系统给每个客户存一个唯一的预计掉保时间。真正执行的时候，只看这个存下来的值。

![预计掉保时间的计算与执行边界](/images/writing/articles/business-experience-part-one/03.webp)

这里得分两件事：算期限，和做到期动作。前者综合规则和有效动作现场算；后者读已经存下来的业务结果。这两件事混在一处写，改规则时就会出事。

改完规则为什么不立刻全量重算？新规则一旦让一批客户当场到期，第二天就是一串客诉和一堆解释不清的对话。

所以改规则只动配置，不动存量快照。确实要重算，先给影响范围，人点过确认再执行。客户那边有了新的有效跟进，按当前规则刷新——这个是自然的，不用问。

日期本身也有边界。新增客户默认走 30 天规则，里面「获取后 30 天未成交」是独立的一条期限。第 20 天你认真跟进了，客户也聊得不错，但一直没签，第 30 天照样掉。跟进能延长「没跟进」的期限，延长不了「没成交」的期限。

这种东西只留在提示词里，解释和执行早晚分叉。我把它写成了规则和用例，让服务给出确定的结果。

## 05 资产怎么递到模型手上

到这一步，问题才真正变成：模型怎么用这些东西。

我没给这个项目单独搭一套聊天服务。业务能力全部暴露成 MCP 工具；Codex 或者别的本地 Agent 当客户端，负责理解任务、挑工具、组织答案。

![Agent、MCP 与业务服务的职责](/images/writing/articles/business-experience-part-one/04.webp)

MCP 只是通道。推理在 Agent 那边；业务服务这侧负责算规则、读数据、判断这个人有没有权限看。

数据落在本地 数据库，业务定义、规则、工具契约放在资产目录。真实 CRM、聊天、电商的接口都留了契约，没接——这一轮只跑本地闭环。

| 内容 | 怎么进到 Agent 的工作过程 |
| --- | --- |
| 术语、对象关系、规则口径 | 按需从业务上下文工具取 |
| 客户、沟通、交易这些事实 | 走带权限的查询工具 |
| 日期计算、归属和保护判断 | 业务服务算，连理由和证据一起返回 |
| 跟进计划怎么排 | Agent 拿事实、目标和用户偏好自己拼 |

权限也落在这层，员工身份绑在服务端，每次调用都查可见范围。

只在提示词里写「你只能看自己的客户」，那不叫权限，那叫建议。Agent 真把别人的客户 ID 传过来，服务得能拒。

## 06 怎么算跑通

第一阶段的目标很窄：Agent 能回答「今天该跟哪几个」，并且说得出依据。

工具给客户状态、近期沟通、交易、保护期限。Agent 再叠上用户当下的意图——这周要回款、要签单，还是只是维护关系——把顺序排出来。

有个细节我改过好几版：客户等级参与排序，但不能替排序说话。一个三个月没动静的大客户，不如今天等着报价确认的中客户。

也是在这儿我把范围收住了：企业共用的定义和约束沉下来，千人千面的偏好留到用的时候再表达。

![销售助理阿单的历史客户查询](/images/writing/articles/business-experience-part-one/05.webp)

*图为后来接入 tigerose「销售助理阿单」后的画面，用来看真实交互长什么样*

只读跑通之后，销售可以用自己的话问，Agent 通过工具拿事实，给一个能追问、能核对的建议。

## 07 走完这一段，剩下什么

我原以为这一步的价值是「把文档沉淀下来」。做完发现不是。

变化在于：这套判断以前只在我和几个老员工的嘴里，现在别的 Agent 通过接口也能拿到，还能说出理由。人走了，判断还在。

能带走的也不是这套字段表。是辨认对象、拆状态、定动作的手法，还有那个习惯——每定一条规则，顺手把为什么这么定一起写下来。

下一篇是 Agent 真的开始改数据。它回了我一句「已录入成功」，然后这个项目进了另一种状态。

如果要从你最熟的业务里挑一条规则，做第一份 Agent 资产，你会挑哪条？
