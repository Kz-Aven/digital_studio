**制造业为什么需要 Agent，又为什么不该轻易替换传统模型？**

供应商发邮件通知某批物料晚到。采购还没把新交期录进 ERP，库存模型和 APS 就继续按旧交期计算、排产。算法没错，输入却过时了。

制造业已经有不少能计算、优化和执行规则的系统。引入大模型，还能多做什么？

## 一、传统算法已经做了很多事

APS 排产，库存模型算补货，ERP 管采购、订单、库存和财务，MES 记录生产、设备、工序和质量。明确、重复的规则，还可以交给规则引擎和工作流。

这些系统积累了多年的工艺约束、业务规则和现场经验，运行相对稳定，结果有一定的可解释性，也已经融入员工的日常工作。

| 成熟的算法模型 | 它在解决什么 | 现在还在不在用 |
| --- | --- | --- |
| 需求预测 | 根据历史销量、订单、季节性预测需求 | 销售与供应链计划 |
| 库存优化 | 计算补货点、安全库存和补货量 | 仓储与采购 |
| 排产优化 | 在产能、工艺、交期约束下安排生产 | APS 的核心 |
| 路径优化 | 安排配送路线、装载量和顺序 | 出库与运输调度 |
| 预测性维护 | 根据传感器和维修记录预测故障风险 | 设备维护与备件计划 |
| 质量检测与 SPC | 监测过程波动、异常和缺陷 | 产线与质检 |

各家企业的部署和收益不同，但这些技术已有明确用途。重建一套稳定的排产能力，意味着迁移规则、重新验证，却未必解决原来的痛点。

我更关心新增大模型或 Agent 能改善哪些工作，尤其是仍靠人读邮件、查系统、解释异常和协调岗位的部分。

## 二、计算、理解和执行，得分开看

### 传统算法能处理的，远不止结构化数据

规则引擎、运筹优化、统计模型、机器学习、传统自然语言处理和计算机视觉，都包含在传统技术的范围内。它们也能处理文本、图像和多源数据，通常需要针对任务设计特征、规则或训练流程。

任务边界、输入输出和评价标准明确时，专用模型能按目标优化、遵守业务约束，结果可重复，也便于验证和定位错误。

如果 APS 已能综合设备、工艺路线、模具、人员、产能和交期生成可执行计划，要重写这套能力，就得拿出准确性、成本或维护方面的证据。

### 大模型擅长应对多变的表达

供应商邮件、老师傅口述、会议决策、维修报告，表达各不相同，有时还要综合多个来源才能读懂。大模型适合协助提取这些信息，理解跨系统字段的业务含义，把零散内容联系起来。

但读懂不等于核实。它可能误读缩写、认错物料、漏掉约束或编造依据。生成的方案仍需规则、专用模型或责任人核验，不能省去数据治理和人工确认。

### Agent 要负责把任务往下推进

大模型负责理解和辅助推理，Agent 则围绕目标安排步骤、调用工具、协调系统并跟踪结果。

| 能力 | 主要职责 | 制造业中的例子 |
| --- | --- | --- |
| 传统算法与业务系统 | 计算、优化、记录、执行规则 | APS 排产、ERP 采购、MES 生产记录 |
| 大模型 | 理解、提取、归纳和辅助推理 | 读邮件、整理异常、提取经验 |
| Agent | 规划、调用工具、协调和跟踪 | 查订单、核交期、调用排产模型、通知计划员并跟踪处置 |

固定步骤可以用工作流完成。遇到模糊信息、路径选择或例外处理，再让大模型参与。按任务分工，比争论技术高低有用。

![Momo 核验并整理信息，交给传统模型计算，Agent 连接任务步骤](/images/writing/manufacturing-ai-models/02-model-roles.webp)

## 三、数据问题不能都归到大模型头上

结构化与非结构化，关注信息的表达形式。订单表、库存表、传感器数值有相对固定的字段；邮件、自由文本、口头经验和会议记录则难以直接放进固定字段。

同构与异构，关注数据之间是否一致。不同来源的数据，可能在字段、编码、口径、时间粒度和语义上存在差异。

ERP、MES、APS 的物料编码都是结构化字段，也可能采用不同规则，需要对齐。一批统一模板的维修报告虽然是文本，结构却可能相当一致。

本体建模、主数据管理和数据治理，可以明确物料、订单、供应商、设备、工序等实体及其关系，对齐编码、概念和口径，并确定维护责任、冲突处理、更新频率和访问权限。这能解决不少实体对齐、语义对齐和数据质量问题。

含糊的供应商消息仍要核实，老师傅的经验仍有适用工况，来源冲突仍要找责任人确认。

本体定义对象和关系，数据治理负责质量和责任，大模型协助理解多变表达，规则和专业模型负责校验与计算。

## 四、大模型能补上的几处工作

### 交期变了，模型还在用旧数据

开头的邮件就是一个例子。库存模型能算补货量，但供应商改了交期甚至规格，ERP 没更新，模型就会继续用旧数据。

Agent 可以提取供应商、物料、订单和交期变化，与 ERP 数据关联，区分已确认和待核实的信息。需要确认的交给采购，允许更新的按权限处理。

事实确认后，再调用原有库存或排产模型，汇总影响、通知相关人员并跟踪后续。邮件里的变化由此进入原有决策流程，无须重写算法。

### 系统各自能做事，协调还靠人

ERP、APS、MES、质量系统和维修系统齐全，也未必能自动协作。

采购读邮件后通知计划员，计划员判断受影响订单、调整排产，生产主管查询现场状态，再由人整理影响、向管理层汇报。员工在系统之间搬信息、补背景、找人确认。

Agent 可以收集上下文、理解异常、调用系统、组织动作并跟踪结果。收益取决于这些人工协调有多少、难在哪里。

若系统集成成熟、流程能够预先定义，接口、规则引擎和工作流可能更简单稳定。文本多、例外频繁、规则难以写全的环节，更值得尝试 Agent。

![Momo 接好系统之间的信息断点，连接 ERP、APS 与 MES](/images/writing/manufacturing-ai-models/03-system-handoff.webp)

### 经验有了，员工遇事还是用不上

老师傅熟悉设备工况、告警轻重、检修顺序和质量波动条件，也知道换了设备或物料，哪些经验可能失效。

这些知识散在口头交流、笔记和维修记录里。即使进了知识库，新员工也未必能联系到当前订单和设备状态。

Agent 可以结合任务检索经验、解释依据，在适用范围内建议，超出范围就提醒找专家。

记录经验时，应保留当时情境、可观察信息、判断依据、排查步骤、动作和结果，以及适用条件、失败案例、反例和升级时机。员工能力是否提高，还得用真实任务验证。

## 五、讨论里，有几处判断需要改

最初直接比较传统算法和大模型，忽略了企业已经建好的系统。补上多年投入、业务规则和稳定性这个前提，问题就变成了新方案能在现有基础上改善什么。

把结构化数据交给传统算法、异构数据交给大模型，也分得太粗。传统技术同样能处理文本、图像和多源数据。实体、口径、时间关联和数据冲突，该治理的仍要治理，关键事实仍要核验。

原先觉得供应链每个节点都有模型，也许就不需要大模型。但单个系统能做事，不代表信息会自动流动、异常有人协调。协作机制成熟，Agent 的新增收益可能有限；仍靠员工来回处理，就值得评估。

我也曾想，系统成熟的企业增强旧系统，数字化程度低的企业直接采用 AI Native。可后者一样需要数据、流程、权限和安全机制。AI 能改变入口，不能跳过基础建设，路线仍要看数据质量、流程成熟度和风险。

至于让应届生借助 AI 拥有老师傅 80% 的能力，这个数字更适合作为愿景。存下经验，并不等于复制情境判断、异常识别和风险意识。先限定任务，验证独立解决率和处理时间是否改善、错误处置及安全质量风险是否增加，再扩大范围。

## 六、落地可以从一条真实业务流程开始

### 先找出人在哪里反复补位

沿着供应商交期变更到生产计划调整的流程，记录信息来源、相关系统、已有模型负责的判断，以及依赖人工理解和协调的步骤。找出信息丢失、延迟、重复录入的位置，标出必须审批的高风险动作。

优先看高频、耗时、跨系统、涉及非结构化信息且结果可衡量的工作。

### 再决定每项工作交给谁

| 任务 | 优先考虑的能力 |
| --- | --- |
| 主数据统一、编码映射、数据质量 | 主数据管理、数据治理、规则校验 |
| 排产、库存优化、确定性计算 | 现有 APS、优化模型或专用算法 |
| 从邮件、维修报告、会议记录提取信息 | 大模型辅助提取与分类，关键事实另行核验 |
| 跨系统查询和流程执行 | API、工作流、权限系统 |
| 理解难以穷举的异常、选择路径 | 在明确范围内引入 Agent |
| 高风险设备控制、重大质量或安全处置 | 既有安全与授权机制，不能仅依赖大模型 |

具体分工还要结合任务、验证结果和风险要求。

### 执行权限一点点放开

从只读查询、整理异常开始，再提供附有数据来源、依据和不确定性的建议。确认后，才允许更新工单、发起流程或调用模型。

低风险、边界清楚、结果可验证的操作，可在权限和规则约束内自动执行。全程监控、记录，失败时暂停、回退或交给责任人。是否继续放权，要有结果作为依据。

![Momo 核验并授权后打开执行闸门，保留回退路径](/images/writing/manufacturing-ai-models/04-authorized-execution.webp)

### 经验要有人维护

从高频、风险可控的异常入手，收集真实案例，由专家整理依据，标明设备、工艺、物料、情境和适用条件，保留成功与失败记录。

让 AI 在真实任务或历史回放中给建议，由专家检查准确性、遗漏、误导风险和升级时机。验证后再纳入知识体系，并指定责任人、记录版本、持续修订，避免沿用过时经验。

### 试点前就记下比较基线

| 想改善的工作 | 可以观察的指标 |
| --- | --- |
| 人工协调 | 每个异常的人工处理时间、跨系统操作次数 |
| 异常处理效率 | 从异常出现到确认、处理、关闭的时间 |
| 新员工能力 | 独立解决率、专家求助率、达到合格水平所需时间 |
| 质量风险 | 错误建议率、错误执行率、返工率、漏报率 |
| 知识复用 | 历史案例命中率、建议采纳率、经验更新及时性 |
| 经济收益 | 节省工时、减少损失，以及集成、维护和模型调用成本 |

试点前后用同一口径比较。回答准确率、调用量和演示效果，代替不了处理时间、错误率和经营结果。指标与门槛按任务设定，不能套用到所有工厂。

## 七、可以先试供应商交期异常

交期变化影响生产计划，适合用来检验系统信息和历史经验能否一起发挥作用。

1. 识别供应商邮件中的交期变化。
2. 关联供应商、物料、采购订单和生产订单。
3. 区分已确认与待核实的信息。
4. 查询库存、生产计划和历史异常案例。
5. 调用现有 APS 或库存模型评估影响。
6. 向计划员提供影响范围、建议、依据和不确定性。
7. 由授权人员确认后执行调整。
8. 跟踪至异常关闭，记录实际结果。

大模型理解信息，现有模型计算，业务系统保存事实、执行确定性流程，人员负责关键决策和授权。

试点要验证人工信息断点是否存在、历史经验能否改善判断，以及保留原模型时 Agent 能否带来可量化收益。也可能发现，更急需补的是集成、治理或知识整理。

边界要提前明确。未经核实的邮件不能覆盖正式订单，审批不能绕过，排产建议必须满足既有约束，高风险操作仍受原有安全与授权机制控制。

建议和执行应尽量记录来源、依据、工具、审批及结果。信息冲突、置信度不足或超出经验范围，就要求核实或交给专家。

## 八、企业为什么要为平台付费

企业买 Agent 平台，要看哪些工作能改善。用了大模型，本身不足以解释这笔钱。

平台得在授权范围内调用 ERP、MES、APS，用对已有规则和算法，结合当前业务给出下一步建议，并协助执行。经验要有来源、验证、维护责任和适用范围；关键动作要有权限、审批、验证、审计和失败处理。

收益则用真实任务衡量，处理是否更快、质量是否改善、新员工多久达到合格水平。

先在一组明确任务上提高新员工的独立解决率、缩短培养时间，且不降低质量、安全和合规标准，比笼统承诺复制老师傅能力更容易验证，也更容易判断值不值得买。

## 九、要不要继续投入，回到任务结果上看

成熟算法运行稳定，就继续用。替换之前，先证明新方案在准确性、成本、维护性或整体业务收益上更好。

大模型能把邮件、文档、会议和经验中的信息接入现有系统，改善算法输入，但核实和治理不能省。

规则明确、流程稳定，API 和工作流可能就够了。语言理解、情境判断、动态规划或复杂例外处理能带来明确收益时，再引入大模型。

知识库不等于经验复制，员工能力仍要靠任务结果验证。AI Native 也可以保留成熟系统，通过新交互降低使用门槛，逐步连接信息、知识、算法和流程，无须推倒重来。

评估项目时，先选一项长期依赖人工理解、跨系统协调或个人经验的高价值工作，记录耗时、错误和成本。等 Agent 参与后有了前后对照，再决定是否扩大范围。
