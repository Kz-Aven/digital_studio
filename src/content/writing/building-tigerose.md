Codex、WorkBuddy 已经很好用了，再做一个个人 AI 助理，是不是多此一举？

如果只是为了完成工作，我完全可以直接用它们。但我做 Tigerose，是想深入研究另一件事：**一个能持续做事的个人 Agent，到底是怎样运行起来的？**

模型为什么选这个工具？任务没做完，为什么就停了？换个模型、加个技能，行为为什么变了？这些问题，只站在使用者的位置，很难看清。

所以，我决定从最简单的 agent-loop 开始，亲手搭出一个本地助理，再一步步补齐它需要的能力、治理和评估机制。

如果你也是产品经理，已经用过 Agent，却还想弄明白“对话框后面发生了什么”，这就是 Tigerose 想与你分享的过程。

## 1. 一个循环，能动手，还算不上助理

起点很简单：接收任务，让模型决定下一步，调用工具，把结果交回模型，再继续。这就是 agent-loop。

接上读写文件，它就能操作本地资料。但很快，产品问题出现了：长任务怎么记住进展？工具报错怎么办？什么时候继续，什么时候问人，什么时候结束？

![会转的循环，不等于已经交付](/images/writing/articles/building-tigerose/01.webp)

于是，循环外面开始长出上下文管理、任务状态、权限和结束条件。

**这些围绕模型、支撑它持续行动的机制，就是我想研究的 Harness。** 它决定的，是用户交出任务后，还要替助理操多少心。

## 2. 从写死能力，到自由配置助理

只把工具接上，还不够。研究助理、写作助理和代码助理，需要的工作方式并不一样。

我逐渐把能力拆成可以按角色配置的部分：

- **Tool**：具体能做什么，比如读文件、执行命令。
- **Skill**：这类工作应该怎么做，把方法和步骤复用起来。
- **MCP**：连接外部工具与数据服务。
- **Plugin**：打包和复用角色、技能等扩展资源。
- **频道**：从飞书、钉钉等日常工作入口接收任务。

再加上模型选择、工作区与权限配置，用户才有可能组装自己的助理，而不是只能接受一套固定能力。

Tigerose 以本地会话、配置和工作文件为基础；接入云模型或外部服务时，必要数据仍会发往对应服务。

这里的产品判断是：**能力自由化，不是默认全部打开，而是让合适的角色拿到合适的能力。**

## 3. 能力越多，越需要 Agent 治理

能调用工具，不代表每次都该调用；能继续尝试，也不代表值得一直尝试。

我开始把“怎么管住它”当成一套治理问题：

权限决定能碰哪些文件、能做哪些操作；目标和任务状态帮助它保持方向；重复调用与预算控制约束空转；需要人判断时，把决定交回来；运行记录则让问题有迹可查。

![把通往交付的路，一段一段补完整](/images/writing/articles/building-tigerose/02.webp)

随后，我把单个助理扩展成多角色协作。用户可以把助理加入项目群，用 @ 派活；在授权范围内，助理之间也能委派任务、补问、交付和要求返工。

但协作也扩大了治理范围：谁能找谁？谁负责验收？加入一个群，是否意味着自动获得其他人的权限？这些都要有明确边界。

![你掌握方向，助理分工协作](/images/writing/articles/building-tigerose/03.webp)

从循环到平台，并不是简单地增加几个 Agent，而是把分工、信息传递和责任关系一起补上。

## 4. 做完没有，要靠评估说话

治理约束过程，评估回答效果。这里我关心两层问题。

第一层是**这次任务是否真的完成**。工具返回成功，与用户目标达成，是两回事。Tigerose 的目标模式会结合任务状态、可用证据和完成度评估，判断是否可以结束；部分操作还有专门的验收检查。

第二层是**这个 Agent 是否稳定好用**。一次演示顺利，说明不了换一种问法、遇到工具故障后会怎样。

为此，我也整理了一套可复用的评估专家配置：从真实任务设计用例，记录可观察的执行过程，再评价目标理解、工具使用、错误恢复、结果质量和效率，并汇总多轮表现。

这是一套评估方法与配置，不代表已经完成了全面基准测试。对我而言，更重要的是建立改进依据：改完一处，究竟解决了什么，又引入了什么问题？

**评估不能只看最后一句话漂不漂亮，也要看它是怎样把事情做成的。**

## 最后，回到一个可靠可用的个人 Agent

走完这条路，我对“可靠可用”的理解更具体了：有明确的任务范围，有按需配置的能力，有执行边界，有交付检查，也有人能接手的位置。

这就是 Tigerose 当前阶段的落点：围绕可检查、可接管的工作，打磨一个可靠可用的个人 Agent。可靠性要在具体任务中验证，不能靠一段演示宣布。

对我来说，这个项目的价值，是把 Harness 从一个听过的概念，变成可以运行、观察、修改和评估的产品。

**Tigerose，心有猛虎，细嗅蔷薇。** 既要有推进任务的力量，也要认真对待让用户放心的细节。
