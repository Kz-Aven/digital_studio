销售助理阿单告诉我，两条客户跟进已经录入成功。

它在回复里写的客户名称是对的。可我后来查了数据库才发现，记录挂到了另一家客户下面。

这件事我在前面的 CRM 实操文章里写过。当时让我后怕的，是它没有报错。

如果只看最后一句“录入成功”，这次任务就会被记成一次成功；如果去看业务数据，就会发现客户关联错了。

这件事改变了我看 Agent 的方式。

![Momo 核对客户文件夹，发现跟进记录可能错绑](/images/writing/articles/agent-evaluation-evidence/01.webp)

这个问题，也让我开始做一个项目：Agent Asset Expert。我想把助理的工作过程留下来，作为复盘、评估和后续改进的基础。

今天先不展开技术细节。我想从这个项目出发，聊聊企业 Agent 治理里的一件基础工作：怎么判断一个 Agent 做得好不好。

## 01 任务结束，不代表事情办对了

企业让 Agent 录跟进、查订单、整理维修建议。只看它最后说了什么，很容易漏掉中间的问题。

结果写得像回事，事情却未必办对。

所以，我现在会把一次任务拆开看：用户希望它做什么，它实际调用了什么，业务系统发生了什么，最后展示给用户的又是什么。

这几处能对得上，才有条件继续判断任务是否完成。

## 02 先给 Agent 留下一份工作档案

员工处理一件业务，通常会有工单、审批记录、操作日志。Agent 做事，也需要一份能回头查看的工作档案。

我在 Agent Asset Expert 里，先尝试留下几类信息：用户提出的任务、助理的最终回复、能采集到的工具活动和运行状态，以及当时使用的部分能力配置。

结果不对的时候，至少有材料可以往回看。

还是拿客户跟进举例。工作档案可以帮助我核对用户说了什么、Agent 回复了什么，以及当时能采集到的工具活动。至于跟进究竟挂在哪个客户下面，仍然要回业务系统核查。

**Agent 的工作记录和业务系统里的实际结果，要放在一起看。**

![Momo 对照工作记录和业务结果](/images/writing/articles/agent-evaluation-evidence/02.webp)

目前这个项目提供的是采集和查询能力。它是否完整记录了某次任务，要看对应平台实际上开放了哪些信息，以及采集链路有没有接好。

## 03 先看清楚：你究竟看到了多少

不同 Agent 平台能提供的信息并不一样。有的平台可以接入运行时过程；有的平台只能通过 Hook 拿到部分事件。

如果页面上只有“记录完整”四个字，读的人很容易以为整条过程都在。

但这里其实有两件不同的事。

第一，**平台提供了多少过程**。如果只能看到部分工具事件，就不能假装看到了全部。

第二，**已经采集到的内容有没有保存完整**。平台提供了数据，也可能在保存时出问题。

在项目里，我把它们分别标记。前者叫覆盖范围，后者叫记录完整性。

![Momo 区分未采集与未保存的信息](/images/writing/articles/agent-evaluation-evidence/03.webp)

而且，即使一条过程记录保存完整，也只是说明我们有了更多复盘材料。**任务对不对，仍然要用业务事实判断。**

## 04 从真实工作中，找到值得评估的案例

有了档案之后，下一步是找案例。

当前项目里，已经可以从非完成状态的任务和有反馈的记录中筛选候选案例。筛选出来以后，还需要人去看：它遇到了什么问题？材料是否足够？有没有业务人员能够确认正确结果？

候选案例不等于正式评测题。成功但没有反馈的优秀案例，也需要主动去找。

比如，某次任务被中断，可能是 Agent 出错，也可能是用户主动取消。只看一个“失败”状态，很难判断它的能力。

如果要把“客户跟进错绑”变成一道评测题，我需要保留原始任务、涉及的客户信息、可见的执行过程，以及业务系统里的实际关联结果。

**有真实任务，有证据，也有可核对的判定标准，才更接近一条能使用的评测案例。**

![Momo 整理任务、证据和判定标准](/images/writing/articles/agent-evaluation-evidence/04.webp)

那次 CRM 错绑是我已经复盘过的真实问题。Agent Asset Expert 是否采集到了那一次的完整过程，还需要另行核实。这里我用它说明希望打通的评估路径。

## 05 评估 Agent，我想先看四个层次

把案例准备好以后，评估还不能只问一句“成功了吗”。

我目前更愿意分四层看。

**第一层，看调用。** 工具有没有正常调用，接口是否报错。这一层可以帮助定位技术问题。

**第二层，看业务动作。** 操作是执行了、被拒绝了，还是因为缺信息停下来等人补充。有时候拒绝越权操作，恰恰是正确表现。

**第三层，看业务事实。** 客户、订单、时间和状态是否真的写对。阿单那次错绑，就是在这一层发现的。

**第四层，看用户收到的结果。** Agent 说的内容是否与实际结果一致。如果只是提交了申请，就不能告诉用户“已经办完”。

这四层不是每个任务都要查得一样深。内部资料整理和正式修改订单，风险不同，核验方式也应不同。

有的任务还需要看效率：处理用了多久，人工复核花了多少时间，是否真的减少了重复工作。只是时间、Token 和成本这些指标，也要先确认采集口径和数据是否可用，不能把没有采到的数据当成零。

## 06 从一组任务开始，慢慢形成评测集

我希望最后形成的评测集，不是一次性整理完就放在那里。

可以先选一条业务流程，比如客户跟进录入。把正常录入、客户名称有歧义、信息缺失、无权操作、写入超时这些情况放在一起。

每个案例都写清任务目标、业务前提、可用证据和判断标准。涉及业务写入的，还要安排合适的隔离环境，避免评估时重复修改真实数据。

模型或工具调整后，可以用同一组案例检查旧问题是否重现。

目前 Agent Asset Expert 走到的是工作记录、查询和候选案例这一步。案例审核、标准答案、评测执行、人工复核和版本回归，还需要继续建设。

## 07 治理从看清工作开始

企业讨论 Agent 治理，很容易先想到权限、审批和安全规则。这些都重要。

但在决定给 Agent 多大权限之前，我想先回答一个更基础的问题：**它过去接过什么任务，实际做了什么，结果有没有被核实？**

有了工作档案，才能找到值得复盘的问题；有了业务证据，才能判断结果；把这些案例积累起来，才能逐步形成贴近企业工作的评测集。

这篇先把框架立起来。后面我会继续拆解：怎样设计评测案例、怎样核对业务结果，以及模型或工具变化以后，如何判断 Agent 是否仍然可靠。
