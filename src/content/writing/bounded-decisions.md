11 月 11 日，Google DeepMind 发布了 Gemini Decision 1 和配套的 Gemini Decisions API。

看到这个消息的时候，我想起了之前研究过的 Jev，以及在本地尝试过的轻量级决策模型 Laya。Jev 今年 9 月中旬发布，Google 的产品出来时，还不到两个月；这段时间里，OpenAI、Microsoft、AWS Strands 和开源社区也都陆续有了动作。

我感兴趣的地方在于，这些产品关注的任务，很多看起来并不复杂。比如给模型一段客户咨询，让它判断应该交给哪个客服组；或者给它一张页面截图，判断当前操作有没有完成、要不要转人工。

这些任务通常不需要一份几百字的分析报告，系统要的可能就是一个选项、一个分数，或者条件成立的概率。但把这样的判断放进 Agent 或企业业务流程里，它可能一天要发生很多次。每次都调用生成式大模型，时间和成本就会慢慢累积。

所以我想借着这两个月的产品变化，聊聊 Decision Model 能处理什么问题，以及它放进 Agent 和企业业务里，可能会怎么用。

## 从 Jev 到 Gemini Decision，这两个月发生了什么

先把这段时间的主要产品整理一下。

| 时间 | 厂商 / 项目 | 模型或产品 | 主要特点 |
| --- | --- | --- | --- |
| 09.15 | TypeSafe AI | Jev | System One 模型，结构化概率决策 |
| 09 月下旬 | 开源社区 | Laya | 轻量级、非自回归、本地部署 |
| 09.29 | OpenAI | Decisions API 限量预览 | 基于 GPT-6 Luna |
| 10.01 | AWS Strands | Strands Decider 2B | 2B 开源决策模型 |
| 10.06 | OpenAI | Decisions API 公开测试 | 面向开发者的结构化决策接口 |
| 10.09 | Microsoft | Microsoft-Decision-1 | 基于 Qwen3.5-9B 后训练 |
| 10 月 | 开源社区 | Open-Jev | Jev 思路的独立开放实现 |
| 10.22 | OpenAI | Decisions API 正式发布 | 支持图像、JSON 和批量决策 |
| 11.11 | Google DeepMind | Gemini Decision 1 | 原生多模态、最多 1,000 个问题 |

这几家走的路线并不完全一样，但关注的问题很接近：当应用只需要从有限结果中做出判断时，能不能用更适合这种任务的方式完成？

### Jev，把判断做成可调用的能力

TypeSafe 把 Jev 称为 System One Model，名字借用了《思考，快与慢》里的 System 1 概念。它面向的是快速、结构化的决策任务。

比如企业客服系统收到一条咨询，需要知道它是否紧急、该交给哪个组、投诉严重程度有多高。Jev 把这类需求整理成几种类型：Noul 用于判断条件成立的概率，Choice 用于从候选项里选择，Score 用于按给定量表评分。

它的设计思路是直接输出软件可以使用的类型化结果和概率，不依赖逐 Token 生成一段文字来表达最终判断。

TypeSafe 在发布文章中报告，Jev 在部分测试工作流中，相比特定对照模型有约 193.6 倍的速度差异和 444.6 倍的成本差异。这里的数字有测试条件，不能直接理解成它在所有任务上都能快几百倍、便宜几百倍。

但这种产品思路让我印象挺深：以前我们想到 AI，习惯让它回答问题、解释过程；Jev 把业务系统里反复出现的判断拿出来，做成了一种可以单独调用的能力。

### OpenAI，从生成模型提供专用决策接口

OpenAI 的路线有所不同。它在 9 月 29 日的 DevDay 公布 Decisions API 限量预览，10 月 6 日进入公开测试，10 月 22 日正式发布，底层使用的是 GPT-6 Luna。

以前让 LLM 判断一条咨询的归属，也可以要求它输出 JSON，甚至通过 JSON Schema 限制格式。Decisions API 则让开发者预先定义问题和合法结果，再由接口返回结构化判断。

所以，结构化输出并不是决策接口独有的能力；专用接口想做的，是针对这类任务继续优化延迟、概率输出、批量判断和成本。OpenAI 官方表示，在相应任务上，Decisions API 相比通过 Responses API 使用 GPT-6 Luna，速度最高可达 10 倍。

这也说明，提供决策能力不一定要从头训练一个独立的新模型，基于已有模型提供专用接口，也是一条路线。

### Google，把更多类型的输入放进来

Gemini Decision 1 支持文本、图片、音频、视频和 PDF 输入，官方披露的上下文窗口最高为 256K Token，一次请求最多处理 1,000 个独立问题。其报告的端到端延迟约为 150–250ms，每百万输入 Token 定价 0.10 美元，输出 Token 不收费。

比如给它一张桌面照片，可以围绕同一份输入判断有没有液体洒出、需要擦拭还是呼叫保洁，以及问题的严重程度。

这里也要说清楚，Google 并不是第一个支持图像输入的 Decision API，OpenAI 在 10 月发布的 Decisions API 已经支持图像。Google 这次覆盖了音视频、PDF 等更多输入类型，也支持更大规模的批量决策。

看到它支持图像时，我第一时间想到的是 Computer Use。Agent 操作电脑时需要反复看页面、判断状态，再决定下一步动作，这里面可能有不少适合交给决策模型的局部判断。

## 什么样的问题适合交给 Decision Model

我目前的理解是，Decision Model 比较适合输出范围明确、输入又带有一定语义复杂度的任务。如果同类判断还会被反复执行，并且能用人工标签或业务结果评估，就更值得拿出来测试。

![复杂输入经过分拣，得到有限范围的判断结果](/images/writing/articles/bounded-decisions/01.webp)

比如客户说：「我买的空调已经维修三次了，昨天又坏了，现在家里老人热得受不了，你们到底能不能解决？」

系统需要理解这段话，判断客户是在投诉，紧急程度较高，可能需要人工介入，再分配给升级售后组。这些结果都可以提前定义好，但客户的表达方式很难穷举。

不过，识别出严重投诉，和决定给客户退款，是两件不同的事。退款还要查询订单、维修记录，核对售后政策、金额和合同条款。模型可以帮助识别情况，后面的业务动作仍然要经过规则和权限系统。

决策模型也有几个容易被高估的地方。它可以从候选项里选择下一步，但不能因此认为它已经能独立完成长期复杂任务；返回了概率，也不代表这个概率天然准确。模型给出 95% 的置信度，是否真的对应业务中的正确率，还需要用数据做概率校准和持续评测。

至于写文章、生成代码、制定复杂方案，或者完成多步骤规划，依然需要生成式模型。大额退款、资金转账、设备安全操作这类事情，即便模型能辅助判断，最终授权也应该交给相应的规则和人员。

## 放进 Agent 里，可以从哪些地方开始

一个 Agent 从收到请求到完成任务，中间要经过不少判断。它需要选择处理流程、筛选检索结果、找到合适的工具；工具调用失败了，还要决定重试、升级还是终止；执行完以后，也需要检查结果是否符合要求。

这些环节里，有些判断可以先用决策模型尝试。例如一个 Agent 接入了包含上百个工具的 CRM MCP，每次都让生成模型阅读全部工具描述，可能增加上下文开销，也会影响工具选择的效率。

一种可以尝试的做法是，先根据用户请求召回一批候选工具，再由 Decision Model 评分，接着让生成模型为选中的工具生成调用参数，最后执行工具。这样做能不能带来收益，还要看候选工具召回得准不准，以及增加一个判断环节后，整体耗时有没有下降。

安全检查也有类似的应用。Agent 准备执行一条 Bash 命令时，可以结合命令内容、执行目录和任务上下文，先做一次风险评分。

OpenAI 在 Decisions API 的发布文章中引用过 Datadog 的实践：执行 Agent 生成的修复命令之前，先用 Decisions API 评分。Datadog 报告，在准确率相当的情况下，p95 延迟降到了此前方案的约 1/40。

这个案例有参考价值，不过风险评分和执行授权仍然要分开。模型可以提示哪里需要注意，命令能否执行，还要由确定性策略、沙箱和审批机制控制。

### Computer Use 是我想继续观察的方向

操作界面的 Agent 通常要反复经历截图、理解页面、推理下一步、执行操作，然后再截图。如果任务比较长，每一步的模型调用延迟都会积累起来。

![Agent 观察界面并执行操作](/images/writing/articles/bounded-decisions/02.webp)

假设 Agent 正在操作 CRM，页面上弹出了一个窗口。它需要判断这是不是权限授权弹窗、当前操作是否完成，或者出现了需要人工接管的异常。这些问题有截图作为输入，也能事先定义有限的判断结果。

如果系统已经识别出「提交」「取消」「返回」等候选动作，决策模型还可以参与选择下一步。Microsoft 在 Microsoft-Decision-1 的官方文章里，也把 Computer/UI Use 的候选动作选择列为适用场景。

但完整任务要复杂得多。比如登录 ERP、创建采购单、查询库存、填写表单，遇到异常后再恢复执行，中间涉及长程规划、动态探索和跨页面记忆。我的倾向是让生成式 Agent 承担这些工作，决策模型处理部分界面状态判断和候选动作选择，执行器再完成实际操作。

这目前还是一个值得验证的方向。Google 发布的低延迟、低成本数据来自决策工作负载，不能直接拿来证明 Computer Use 的整体成本下降了多少，或者任务成功率提升了多少。

真要比较，得用同一套 GUI 任务一起看完成率、执行步骤、每步延迟、误操作和人工接管情况，再算完成一个任务的总成本。只看单次判断快了多少，可能会漏掉后面多走的步骤。

## 沿着业务流程，找那些反复出现的判断

比起单独列一堆应用场景，我更想沿着一条业务链来看。企业真正关心的通常是客户有没有少转几次、工单有没有更快处理完，而模型只是流程中的一个环节。

### 电商售后，先把咨询分到合适的人手里

一条售后流程可能是这样：客户发起咨询，系统判断问题类型和紧急程度，分配给客服组；客服查询订单和售后记录，确认处理方案，再执行退款、退货或关闭工单。

假设客户说：「快递显示已经签收，但我根本没有收到，快递员也不接电话。」

![售后咨询分流到合适的客服组](/images/writing/articles/bounded-decisions/03.webp)

这段话没有直接说「物流异常」，用关键词规则可能分不准；生成模型能理解，Decision Model 也可以结合咨询内容、订单状态和客服组定义，选择合适的处理团队。如果每天要处理大量类似咨询，就值得把几种方案放在一起比较成本、延迟和分流准确率。

后面的订单查询应由系统 API 完成，退款资格交给规则引擎核对，客户沟通可以交给 LLM 辅助生成，涉及争议时再转人工审批，退款动作由交易系统执行。

我觉得这里最值得关注的是分诊效果。如果错误分流减少，客户不用在多个客服组之间反复转接，客服也能少做一些重复处理，问题解决时间才有机会缩短。至于能改善多少，需要实际业务数据来验证。

### B2B 销售，判断意图和下一步行动

销售线索进入 CRM 后，通常要经过分级、分配、需求确认和商机推进。每个环节都有判断，但判断所需的数据并不一样。

比如客户在官网留言：「我们有 200 多名销售，希望能自动分析每天的销售通话，识别客户意向。下周可以安排一次产品演示吗？」

销售团队需要判断客户有没有明确需求、应该分给 SMB 还是 KA 销售，以及下一步是发资料、电话跟进，还是安排演示。Decision Model 可以结合留言、企业规模和产品线，辅助完成这些判断。

但如果要根据客户行业、规模和历史成交数据预测成交概率，企业现有的传统机器学习模型可能已经做得不错，成本也可能更低。没有必要因为有了新模型，就把原来的方案全部替换。

一条可考虑的分工是：传统 ML 预测成交概率，Decision Model 理解客户意图、辅助选择下一步行动，LLM 生成沟通内容，CRM 规则负责业务流转。实际效果仍要用企业自己的数据比较。

### 制造业维修，先判断知识是否适用

制造企业的设备维修流程里，也有故障分类、紧急程度判断、班组派工和维修知识检索等环节。这里讨论的是维修业务流程，设备的实时安全控制不适合交给这类语义决策模型。

其中我比较关注知识检索后的判断。很多企业有设备手册、维修工单、质量记录，也有老师傅留下的经验文档。这些内容进入知识库后，可以通过 RAG 检索，但检索结果相似，并不代表拿来就能用。

比如都是电机异响，设备型号、运行条件和历史故障原因不同，处理方法也可能不同。能够确定核验的型号、版本和设备状态，可以先由规则和数据系统过滤；剩下需要结合文字和上下文判断的部分，再让 Decision Model 辅助评估案例是否适用。最终怎么维修，还是由维修人员决定。

![筛选适用于当前设备的维修知识](/images/writing/articles/bounded-decisions/04.webp)

把售后、销售和维修放在一起看，会发现它们都有分类、分配、优先级和升级处理等需求。这给了我一个产品化的想法：有机会复用一套判断能力，再根据业务配置输入、候选结果、约束和评测标准。

不过，能力可以复用，判断标准不能照搬。电商投诉的「紧急」和设备故障的「紧急」，对应的业务后果完全不同，训练数据和 Benchmark 也需要针对各自领域准备。

## 规则、传统 ML、LLM 和 Decision Model，怎么选

这些业务判断，并不是到了 Decision Model 出现才有人解决。企业已经有规则引擎、文本分类器、传统机器学习模型，也可以直接调用 LLM。选型时，我更关心任务和现有方案是否匹配。

拿售后路由来说，如果规则是「包含退款关键词就交给退款组」，实现简单、速度快，遇到明确表达也很稳定。但客户说「快递明明显示签收，我却什么都没收到」，句子里没有「物流」两个字，关键词规则就可能漏掉。规则可以继续增加，但表达越来越多时，维护也会越来越麻烦。

这类输入需要理解语义、结果又限定在几个客服组里的任务，可以考虑用 Decision Model 试试。反过来，如果业务规定退款金额超过 1 万元必须审批，直接由规则执行更清楚。

LLM 也能处理客服分类，还能输出符合 JSON Schema 的结果。只是系统如果反复从几个选项里选一个，需要比较完整调用的成本和延迟，尤其 Agent 的一次任务可能包含多次判断，每一步的等待都会累积。

Google 官方披露，Gemini Decision 1 在其测试套件中的成本，约为通过 Interactions API 使用 Gemini 3.5 Flash-Lite 的五分之一。

我会先按下面的方向筛选，再用同一套业务测试集比较。

| 判断类型 | 可以优先考虑 |
| --- | --- |
| 明确的政策、权限和金额条件 | 硬编码或规则引擎 |
| 结构化数据的统计预测 | 传统机器学习 |
| 有限候选项之间的语义判断 | Decision Model |
| 复杂推理、规划和内容生成 | LLM |
| 高风险、争议性决策 | 人工参与，加上系统约束 |

比较时除了准确率、延迟和成本，还要看概率校准以及不同错误带来的损失。普通咨询被误分到人工组，和严重投诉被误分到普通客服组，虽然都算一次错误，业务后果却不一样。

## 专业模型多起来以后

这次值得关注的还有开源社区。Laya、Open-Jev、Strands Decider 等项目，正在探索不同规模的决策模型；其中 Laya 支持本地运行，也提供领域微调、概率校准和评测工具。

Laya 的项目文档展示过，在特定类型化决策测试中，领域微调后的模型明显优于未微调的基础版本。这不能说明小模型在所有业务里都能超过大模型，但对于任务定义清晰、有足够数据、能够持续评测的场景，专门优化的小模型值得拿来比较。

我越来越觉得，一个企业 Agent 后面可能会同时用到好几种能力。复杂任务交给生成模型规划，知识检索用 Embedding 和 Reranker，部分分类和路由交给决策模型，设备或库存预测用时序模型；权限、政策和安全约束则由确定性规则把住。

模型多起来，系统也会多出一些工作：什么时候调用哪个模型，结果冲突怎么办，升级某个模型后会不会影响整条流程。这些问题需要通过路由、编排和业务评测慢慢解决。

从 Jev 到 Gemini Decision 1，我感受到的变化是，大家开始更认真地把「判断」从一整次生成中拿出来看。

以后遇到一个业务需求，我也会多问自己几句：它的结果是不是有限的？需要复杂推理吗？每天会发生多少次？如果判断错了，后面会有什么损失？

先把这些问题想清楚，再去比较规则、传统模型、Decision Model 和 LLM。对企业来说，模型名称固然值得关注，最后还得看它放进业务流程以后，能不能稳定地解决问题，成本又是否合适。
