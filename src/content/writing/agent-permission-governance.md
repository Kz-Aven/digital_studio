## 客户问订单做到哪了，Agent 怎么回？

我做过一个1688制造业的 AI 业务跟单员，跑在业务员的个人微信上。客户来问订单做到哪了，Agent 先拿微信好友（客户）身份去 CRM 里找对应的客户，再查订单，顺着订单找到 MES 里的生产工单。查到进度后，由大模型组织语言，在微信上回给客户。

这件事听起来就是查几个系统，再回一条消息。真正做的时候，有一步其实比查订单还靠前，就是先看这个客户到底归谁负责。

比如，业务员 A 负责客户甲，业务员 B 负责客户乙。客户乙也可能加过 A 的微信，但这回就算消息发到了 A 的手机上，A 的跟单 Agent 也不能顺手把客户乙的订单查出来。这种情况直接交给业务员处理。我们用的是企业原来就有的业务关系，从业务员到客户，再从客户到订单和工单，沿着这条线决定能查到哪一步。后来回头看，这就是基于关系的访问控制（ReBAC）。

还有一种情况，客户是自己的，订单也查到了，但生产有异常，可能赶不上原定交期。这个信息 Agent 得知道，知道了才明白为什么该停下来。至于怎么跟客户解释、要不要给一个新的日期，就交回给业务员。正常进度可以自动回，异常或可能延期就走人工。

![制造业订单跟进流程，客户归属不符或存在异常和延期风险时转人工，其余情况组织语言后微信回复](/images/writing/agent-permission-governance/01-order-follow-up.webp)

一开始我们把这件事做成了跟单流程里的几条规则。账号托管解决的是 Agent 代表谁，客户归属解决的是能查哪些订单，人工接管解决的是查到了以后，哪句话该留给业务员自己说。这个场景能跑起来，靠的就是把这几个地方想清楚。

## 做官网客服时，员工账号就用不上了

我们后来做了官网客服。企业超级管理员在平台上创建一个 Agent，把它嵌进官网。它平时干两件事，根据授权知识库回答企业、产品和服务相关的问题，有潜在客户留下联系方式时，把信息写回 CRM。

来问问题的人可能第一次打开官网，连企业账号都没有。于是我们给官网客服单独授权。超级管理员管创建和配置，访客可以发起咨询、提交联系方式，真正访问知识库和写入 CRM 的是 Agent。设计这类对外岗位时，我会把范围收在审核过的对外知识和录入客资需要的 CRM 操作里。

财务专员也是独立授权，但服务对象换成了全公司的员工。比如员工当天开了发票，上传报销系统时提示识别不了，他可能就去问财务。操作手册里已经有解释，当天的票可能还没同步到财税系统。这种事用配置了财务制度、报销政策和操作手册的 Agent 就能解答。员工打开财务专员问一句，能拿到流程指导，财务部门的其他资料和报销审批权限仍归各自岗位管理。

再看 CEO 助理，正好能看出另一头的情况。它只服务 CEO 本人，能管理钉钉日程、组织会议、整理纪要、通知参会人。如果被通知的人过了一段时间还没回复，它还可以用授权设备打电话催促。至于等多久可以打、能打给哪些人、最多打几次，都可以再做成具体的行为规则。

![四个 Agent 的使用者范围和执行权限广度，CEO 助理服务专属用户并具备较广的执行权限，财务专员和官网客服服务范围更广](/images/writing/agent-permission-governance/02-access-and-execution.webp)

把这几个岗位摆在一起，我才觉得，谁可以用这个 Agent，要和它可以做多少事分开配。财务专员给全员用，日常做的是问答。CEO 助理只给一个人用，手里却有日程、会议和设备。传统软件按岗位分配角色和权限的 RBAC 思路，在这里也用得上。

独立授权可以先做到在平台上给每个 Agent 单独管权限。至于执行时用专用服务账号、受限的 API 凭据，还是经授权的用户身份，要看接入的业务系统支持什么。

## Skill 发下去之后，还得管实际怎么跑

专业 Agent 多了，平台里也开始积累 Skill、MCP、知识库和系统连接。文档处理、数据分析这类通用能力，可以发给员工或部门，让他们按自己的工作需要给助理配置。排产、财务审核、业务跟单这类专业能力，则可以由管理员发给指定的岗位 Agent，员工通过岗位 Agent 获得服务。

这里还有一个配置权。员工能用某个 Skill，要不要允许他把它装到另一个 Agent 上，是个单独的决定。特别是那个 Agent 要放到官网上时，一次安装就可能改变外部用户能接触到的信息。

![企业能力中心的两条分发路径，员工按授权领用和配置能力，管理员直接给专业 Agent 授权，运行时仍检查工具、资源和行为](/images/writing/agent-permission-governance/03-capability-distribution.webp)

拿生产订单分析来说，Skill 可以写清楚先查客户、再查订单，最后到 MES 确认进度。真要跑这一遍，还要有能调用的 MCP 工具或 API，以及工具背后相应的数据权限。把 Skill 卸下来，Agent 如果还握着 MES 的工具和凭据，仍可能通过其他路径查数据。

即使用的是同一个 CRM MCP，销售助理可能只查当前销售人员负责的客户，业务跟单员还要查这些客户的关联订单，经营分析员则可能只需要跨部门的汇总数据。到了运行时，我会继续拆开看，当前工具能不能调，这条记录在不在范围内，以及这次允许读、创建、修改还是删除。技能市场能把能力发出去，这些判断决定了能力落到业务系统里具体能干什么。

## 接进飞书和钉钉后，群里谁会看到？

接 OA 通道时，我们的做法是绑定时人工确权，记录对面是哪个私聊用户，或者哪个群。这样可以先把入口的使用范围定下来，暂时省去同步飞书、钉钉里整套用户权限的工作。

私聊和群聊都可以用 Agent，也都可以问各自获准披露的知识库内容。业务系统只在已确权的私聊里、按 Agent 的授权范围读取。群聊这边，我们直接把业务系统访问关掉了。

想象一下，销售总监在群里让 Agent 统计整个部门的业绩。总监有权看，但 Agent 要是把结果回到群里，群成员也都看到了。要开放这个功能，除了识别发起人，还得知道群里有哪些人、每个人能看什么。早期先把群聊留给知识问答，业务数据走私聊，场景就能往前做。

![Momo 把装有业绩数据的信封投进私聊信箱，群聊公告栏上没有这份数据](/images/writing/agent-permission-governance/08-momo-disclosure.webp)

后来还有一处要处理。Agent 刚在私聊里查完数据，群里有人问它刚才查到了什么。如果这两个地方共用一个 Session，它从历史消息里就能拿到答案，根本不用再调工具。于是我们让私聊和群聊各用各的 Session，连同历史和上下文一起隔开。

![飞书和钉钉通道绑定经人工确权，私聊和群聊使用独立 Session，只有已确权私聊能在授权内读取业务系统](/images/writing/agent-permission-governance/04-channel-isolation.webp)

通道身份和会话隔开之后，群成员变化、员工离职、授权撤销，还要靠后续的身份复核和权限失效机制来处理。将来要是接入跨 Session 的长期记忆或共享工作空间，那些文件、记忆和缓存也得有自己的访问边界。

## 回头看，做一个 Agent 要问清哪六件事

前面几次做项目，权限都是跟着业务问题冒出来的。回过头再看，我会把它们归到六个问题里。比如还是那条微信订单消息，从接进来，到查系统，再到发出去，每一步要用的判断其实都能在这里找到。

![一次 Agent 任务的六个权限问题，分别核对身份、使用者、能力、资源、行为和披露对象](/images/writing/agent-permission-governance/05-six-dimensions.webp)

| 权限维度 | 制造业业务跟单员 | 官网客服 | 财务专员 | CEO 助理 |
| --- | --- | --- | --- | --- |
| 身份 · 代表谁 | 托管业务员身份 | 独立授权的客服岗位 | 独立授权的财务咨询岗位 | CEO 的专属助理 |
| 使用 · 谁能找它 | 业务员负责的微信客户 | 官网访客 | 全公司员工 | CEO 本人 |
| 能力 · 能调什么 | CRM、订单、MES 查询 | 知识库问答、CRM 回写 | 财务知识问答 | 钉钉日程、会议、授权设备 |
| 资源 · 能碰哪些数据 | 负责的客户及其订单、工单 | 授权的对外知识和 CRM 客资入口 | 财务政策和操作手册 | 授权的日程、会议和设备 |
| 行为 · 可以做什么 | 查询、回复、转人工 | 回答问题、录入客资 | 解答和流程指导 | 组织会议、通知、电话催促 |
| 披露 · 可以告诉谁 | 正常进度回给对应客户，异常交业务员 | 对访客开放的信息 | 对员工开放的财务指导 | 按会议和任务的接收对象披露 |

我会把这张表当成设计岗位时的核对清单。六个问题可以落在现有的业务规则、工具授权和通道配置上。比如做跟单员的时候，客户归属校验就能在查订单之前解决资源范围的问题，已经有的 CRM 关系可以直接用上。

## 做到哪一步，就把那一步的权限管好

如果让我从头再做一次，我还是会从一个具体岗位开始。先把跟单场景里的身份、客户归属、正常回复和异常转人工跑通。做官网客服和财务专员时，再把岗位自己的授权和使用范围管起来。等 Skill 和 MCP 多了，再做能力分发。最后，交互入口伸到飞书和钉钉时，把通道确权和 Session 隔离补上。

![从 V1 账号托管到 V4 通道治理的四个实践阶段，V5 统一治理是后续建设方向](/images/writing/agent-permission-governance/06-governance-roadmap.webp)

这四段是我们在项目里逐步碰到的事。各自都可以在当时的业务范围里闭环，就像群聊只做授权知识问答，照样可以先提供服务。等到好几个岗位都在重复写权限判断，再考虑 V5，把共用的部分放进 Agent Harness。

我想做的 Harness，大致是一条从任务入口到结果出口的执行链。入口核对身份和使用范围，加载会话或记忆时检查上下文权限，加载 Skill 和调用 MCP 前检查能力授权，动到业务系统之前再核对资源和操作。真正发消息的时候，还要看接收者和通道能不能收这份结果。共用的策略可以返回放行、请人确认或拒绝，授权决定和实际做的操作一路留下记录，用来审计和复查。

![统一治理设想，Harness 在入口、上下文、能力、执行和输出环节校验权限，并连接统一策略和全程审计](/images/writing/agent-permission-governance/07-harness-checkpoints.webp)

CRM 的客户归属、ERP 的订单权限、MES 的生产数据权限，仍然交给各自的业务系统或可信接口校验。Harness 要做的是把校验接在实际执行的地方，让任务走到哪一步，就得经过那一步的权限判断。统一策略、授权撤销、审计和治理评测，都是这一步往下做的内容。

写到这里，我想起的还是那条问交期的微信。订单正常，Agent 查完直接回，业务员就少追一次进度。真可能延期了，业务员接过这条消息，还有机会先去确认生产情况，再决定怎么跟客户谈。多做一点、什么时候停下来，这两件事得在同一条业务流程里说清楚。说清楚以后，才有底气把下一件事也交给 Agent。
