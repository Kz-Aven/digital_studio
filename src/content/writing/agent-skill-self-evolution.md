我在做 Tigerose 时，发现有些问题很难靠换一个更强的模型解决。

比如我让数据助理「辣小美」查一张表，看看有没有空值和重复记录。结果发过来了，但它没把用来检查的脚本留在工作目录。我在对话里回了一句：「算错了：你没有把检查用的脚本留在工作目录，我无法复核你的计算。」

这句话看着像在挑一个交付细节，背后其实是个产品问题。我今天让它补交，当前任务就能收尾。可同事明天开个新会话查另一张表，还是可能遇到同样的事。只要这条要求没有进入助理平时查表所用的工作规则，就得有人再教一遍。

做企业产品时，这类反馈太常见了。产品上线一年，公司怎么报数、怎么核对、出了例外找谁，早就比上线时多了许多细节。过去，业务同事把这些变动告诉产品经理，产品经理再排期改。现在有些规则已经写成了 Agent 能直接读取的 Skill，改动往往只涉及几行说明。我想试试，从听懂反馈、改出一版，到证明改动有效，Agent 自己能接手多少。

我把这条链路做进了 Tigerose。试点已经跑过自动启用、拒绝启用和回滚。整个过程里最让我意外的是，有一版在固定测试里从九次过一次进步到九次过八次，最后还是被拒绝了。

## RSI 为什么值得产品经理关注

RSI 是递归自我改进。以 Tigerose 这次的做法来说，Agent 每天用一份 Skill 干活。它从任务和反馈里发现工作规则有缺漏，就提出修改。改过的版本通过检查后，会进入之后的任务，还能成为下一次修改的起点。这就是这里的「递归」。

![Momo 把用户纠正加入下一版工作规则](/images/writing/agent-skill-self-evolution/01-feedback-to-skill.webp)

过去讨论 RSI，经常讨论怎么让 AI 参与训练下一版模型。对做 Agent 产品的人来说，还有一层离我们更近。决定助理怎么干活的，除了模型，还有它能用什么工具、看到哪些信息、按哪套规则做事。这些都在 Agent 的运行框架里，也就是常说的 Harness。我这次只动其中一处，改写给助理看的 **Skill 正文**。模型、工具权限和发布条件由系统控制。

我认为，**让 Agent 从实际工作中持续改进，会是接下来 Agent 产品的一条重要趋势**。因为越深入业务，越多决定结果好坏的要求，要等它真的开始干活才会暴露。比如检查表格后要交脚本，这事对写模型的人可能无关紧要，对拿结果去核对的人却很重要。一套通用能力发到不同团队，迟早要磨合各自的工作方式。

这件事也跟记忆有关，但我更关心这个产品上的差别：助理可以记得「我喜欢它附上检查脚本」，而一条写进 Skill、带着测试通过记录的规则，能在同一个团队里交给下一位使用者，也能在改版后重新检查。这样的反馈积累下来，产品才有机会接住越来越多的业务细节。

## 我先从一条可验证的反馈做起

我选了表格质量检查做试点。重复记录怎么算，数据里能查。脚本有没有留下，工作目录里也能看。先在这种任务上做，我才好判断改动到底有没有效果。

一条纠正进来，系统先回看被纠正的回复、原始任务和当时实际用的 Skill 版本。如果能找到和这次问题相关的工作规则，就试着改一版。然后用同一个模型、同一套工具，在隔离的环境里，让新旧版本分别做同样的任务。拿来试改的题和最后决定能不能启用的题分开，关键任务还会多跑几次。因为即使用同一个模型、同一道题，我也遇到过三次里一次失败、两次成功。

刚开始我让系统每次只改一版，三次从对话触发的改动都没达到发布条件。后来才让它拿着上一轮失败的证据继续改，试几种写法，再挑表现好的去做最终检查。有一轮，第一版把统计规则补清楚了，但跑完还是不交文件。下一次改动就有了具体的着力点。这个过程一轮可能花二十多分钟，试得更细，成本也确实上来了。

不过，最麻烦的还是怎么判断它变好了。我一开始把数字算对和交出检查脚本合在一个通过条件里。结果两个版本只要都漏交脚本，就一起得零分。看着是一张挺规整的测试成绩表，其实我连哪一步做对了都看不出来。

后来又碰上开头说的那一版。固定测试各跑九次，旧版通过一次，新版通过八次。但是那回我指出的问题是，**回复里要告诉我用的是哪个检查脚本**。新版还是没写出文件名。我下次要复核，照样得自己找。于是系统保留了旧版。

![新版九次过了八次，仍因缺少文件名被拦下](/images/writing/agent-skill-self-evolution/02-release-gate.webp)

这版能被拦下来，是因为我在流程里加了一条检查。能重做用户碰到的问题，就用原任务让新旧版都试一遍，确认旧版确实出错，新版确实解决。后来我重新安装应用做验收，旧版漏交脚本，新版交了，另外三项固定测试各做三次，旧版九次全挂，新版九次全过。系统自动启用了新版，我开了个新会话确认它确实生效。接着再提一条纠正，系统没找到更好的写法，就保留当时的版本。最后我执行回滚，之后的新会话又用回了原版。

平时默认还是人审核。用户能在原对话看到检查结果，点进去能看到改了哪几条、哪些任务是怎么通过的。选择让系统自动启用，原问题就必须有可验证的改善，关键任务也不能退步。已经开始的会话继续用自己开工时的版本。

## 这条路，已经有别的团队在走了

做 **Hermes Agent** 的 Nous Research 已经让助手能从经验里创建和修改 Skill，也开源了专门试改工作规则的工具。它会比较不同写法的效果，最后把改动交给人审核。这和我在 Tigerose 做的事情很接近。我更想试的是，业务用户能不能直接在原对话里提出纠正、看到进展，再决定用不用新版。[Hermes 官方文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills) · [Nous Research 公开项目](https://github.com/NousResearch/hermes-agent-self-evolution)

**Anthropic** 分享过 Warp 的实践。一个助手负责审查代码，另一个定期读大家对审查结果的反馈，再提议改动工作规则。人审核通过后，新的审查任务就用改过的规则。这个案例让我觉得，定期归拢真实反馈，也许比每收到一条意见就跑一次改进更适合日常工作。[Anthropic 的 Warp 案例](https://claude.com/resources/articles/how-warp-builds-self-improving-agents-on-claude)

**OpenAI** 也公开演示过，把任务执行记录和反馈变成可以重复运行的测试，再根据结果交给 Codex 改进 Agent 的运行框架。它是一套示例，用的范围比单份 Skill 更广，指令、工具和交付要求都能成为改进对象。[OpenAI 的公开示例](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)

回头看，我在 Tigerose 里最想验证的，还是一个挺朴素的问题。用户今天花时间纠正了助理，明天能不能让另一位同事少踩一次同样的坑？做完这次试点，我知道这条路可以走通。接下来得把它放到更常用的任务里，看有多少次纠正值得留下，又有多少次真的能留下来。
